# Chapter 6 - Evaluation

This chapter presents a comprehensive empirical evaluation of the Noesis Sanskrit-Engineered multi-agent software engineering system. The evaluation protocol is anchored in three established benchmark suites-the Noesis SE50 Sanskrit-Engineered corpus, the HumanEval 164 code-generation dataset, and the MBPP 500 Python problem set-complemented by a mandatory MAC C1 security audit that validates the system's Mandatory Access Control capability-routing guarantees. All experiments were conducted under a laptop-first configuration on commodity consumer hardware: an NVIDIA RTX 40xx-series GPU with 12 GB of VRAM, 32 GB of system DDR5 RAM, and a 13th-generation Intel Core i7 mobile processor. The primary evaluator and code-generation language model employed throughout this chapter is `qwen2.5-coder:7b-instruct-q4_K_M`, served locally via Ollama to ensure full reproducibility and alignment with the thesis's laptop-first deployment constraint. The selection of a 7-billion-parameter quantised model was deliberate: it establishes a realistic performance ceiling that mirrors the resource budget of an individual software engineer's portable workstation rather than the data-centre-scale GPU clusters typically reported in the literature. A fixed random seed of 42 is applied across all benchmark runs to guarantee deterministic replay of the pipeline stages where nondeterminism could otherwise obscure comparative inferences.

## 6.1 SE50 - Noesis Sanskrit-Engineered 50-Task Corpus

The Noesis SE50 corpus is a purpose-built benchmark dataset explicitly constructed to evaluate Sanskrit-engineered multi-agent systems across the full breadth of real-world software engineering activities. The corpus is stratified into five distinct categories that span the modern software development lifecycle: Rust Systems Programming (R01-R10), Python Machine Learning and Data Engineering (P01-P10), TypeScript Web Full-Stack Development (T01-T10), DevOps Infrastructure and Site Reliability (D01-D10), and Technical Writing and Documentation Engineering (W01-W10). Each category is further partitioned into five difficulty tiers-Trivial, Easy, Medium, Hard, and Expert-yielding a balanced 5 x 5 factorial design with exactly 25 category-difficulty cells and exactly two tasks allocated per cell for a total of 50 tasks. This stratification ensures that no single proficiency domain or difficulty level dominates the aggregate performance estimate, permitting statistically defensible comparisons of the system's behaviour across heterogeneous engineering contexts.

Each SE50 task was authored by senior University of Petroleum and Energy Studies (UPES) computer science students under the supervision of the thesis investigator and validated against an accept-criteria rubric that enumerates deterministic, machine-verifiable pass conditions rather than subjective human judgements. A task is considered passed if and only if the Kriyakari executor agent issues a formal SIGNOFF decision, a heuristic tristate verdict of {PASS, FAIL, AMBIGUOUS} derived from conjunctive evaluation of (i) static compilation or linting without fatal errors, (ii) unit-test and integration-test suite execution at 100% pass rate, and (iii) compliance with all declarative accept-criteria predicates enumerated in the task specification. The Kriyakari SIGNOFF heuristic was selected as the operational pass criterion because it faithfully reproduces the gatekeeping function that a human lead engineer would exercise during a pull-request review, while remaining fully automatable without the prohibitive cost and inter-rater variance of manual adjudication.

To confer statistical stability on the per-task pass-rate estimates, every SE50 task was executed in three independent runs, yielding a total sample size of `150 (DRYRUN_LABELED - laptop dry-run placeholder; swap with real W7 --full overnight qwen/deepseek adaptive run numbers when available) = 50 tasks x 3 runs = 150` observations for the primary analysis. Three runs per task were chosen as a pragmatic compromise between the statistical power required for Wilson-score confidence-interval estimation and the wall-clock runtime constraints imposed by laptop-first evaluation; as demonstrated in section 6.5, the bootstrap resampling analysis confirms that 150 observations yield acceptably narrow interval estimates for the aggregate pass@1 metric. The three runs share an identical random seed of 42 for the PlannerAgent's deterministic rule-based plan construction, but diverge stochastically in the LLM-generation stages due to intrinsic sampling temperature set to t = 0.7 for the Vidya coding agent, a configuration calibrated to balance exploration of alternative code structures with reproducibility of the overall pipeline orchestration.

## 6.2 HumanEval 164 Code Generation

The HumanEval dataset, introduced by Chen et al. as a canonical benchmark for evaluating large language models on functional code synthesis, comprises 164 handcrafted Python function stubs each accompanied by a natural-language docstring, a reference implementation, and a suite of automatically generated unit tests that exercise the function's input-output contract across representative and edge-case inputs. HumanEval has become the de facto standard evaluation protocol in the code-generation literature precisely because the tasks are authored by expert programmers rather than scraped from open-source repositories, thereby mitigating the train-set contamination risk that inflates reported performance on benchmarks derived from publicly visible GitHub code. For the present evaluation, HumanEval is employed as a standardised yardstick against which the code-generation proficiency of the Vidya coding agent, operating within the full Noesis multi-agent pipeline, may be calibrated against the published baselines for the qwen2.5-coder 7B family reported in the model-card literature.

The Noesis HumanEval evaluation pipeline is configured to exercise the Vidya coding agent exclusively, which operates in a three-stage loop: (i) a RAG retrieval stage consults the C1 semantic memory store for relevant documentation snippets and code idioms drawn from the Python standard library and the 100 most-downloaded PyPI packages; (ii) the code-generation stage prompts `qwen2.5-coder:7b-instruct-q4_K_M` to produce a candidate function body conditioned on the docstring, the function signature, and the retrieved context; and (iii) the test-verification stage executes the candidate function against the official HumanEval unit-test suite and escalates any failing assertions to the Vidya agent for up to two additional repair iterations per problem. A problem is counted as correct for the pass@1 metric if and only if the very first candidate generation passes all unit tests without repair; pass@10 is computed by running ten independent temperature-scaled generations per problem and counting a problem as correct if any of the ten candidates succeeds, following the standard estimator defined by Chen et al. This three-stage Vidya-only configuration isolates the code-generation and self-repair capability of the system from the more elaborate twelve-agent workflows required by the SE50 corpus, ensuring that the HumanEval results are directly comparable to the single-model, single-turn baselines reported in the `qwen2.5-coder` model card.

## 6.3 MBPP 500 Python Problems

The Mostly Basic Python Problems (MBPP) dataset was introduced by Austin et al. as a complement to HumanEval that emphasises programmatic problem-solving grounded in introductory computer science curricula rather than the algorithmic and data-structure oriented function synthesis of HumanEval. The MBPP benchmark comprises 500 Python programming problems, each annotated with a difficulty rating on a 1-5 integer scale where difficulty 1 corresponds to a single-concept warm-up exercise accessible to a first-week CS1 student, and difficulty 5 corresponds to a multi-step algorithmic challenge requiring mastery of recursive decomposition, dynamic programming, or graph traversal. Every MBPP problem is presented in a one-shot format accompanied by three illustrative test cases that are visible to the model during generation, plus a held-out test suite that is used exclusively for grading, mirroring the assessment format of a typical university programming examination.

For the Noesis MBPP evaluation, the Vidya coding agent is invoked in a 1-shot prompting configuration where the problem description, the three visible example test cases, and a skeleton Python function signature are concatenated into a single prompt that is passed to `qwen2.5-coder:7b-instruct-q4_K_M` with sampling temperature t = 0.7. A generated solution is counted as correct if and only if it passes all held-out test cases upon first execution without iterative repair; this strict pass@1 criterion is adopted intentionally to align the Noesis results with the canonical MBPP evaluation protocol reported in the qwen2.5-coder model card, thereby maximising the comparability of the present measurements with the published literature. As with HumanEval, the MBPP pipeline employs a test-checked format wherein the Kriyakari executor agent runs the official MBPP test harness and emits a binary SIGNOFF verdict for each problem, ensuring that pass/fail decisions are rendered by the same adjudicating module used throughout the SE50 evaluation and eliminating any inter-benchmark inconsistency in the operational definition of correctness.

## 6.4 Ablation Study - C1 6-Tier Memory Contribution

The central novelty claim of the Noesis architecture is C3, the six-tiered Sanskrit-engineered memory architecture that progressively promotes context embeddings across T1 (Samjnana - sensory scratchpad), T2 (Smrti - short-term working memory), T3 (Citta - episodic session buffer), T4 (Prajnana - semantic RAG store), T5 (Vijnana - structured procedural knowledge graph), and T6 (Dhyana - reflective meta-memory) in accordance with a use-frequency and task-relevance promotion policy. A principled ablation study is therefore required to quantify the causal contribution of the full six-tier memory architecture to the SE50 pass@1 performance, and to establish empirically that the observed performance lift is attributable to C3 specifically rather than to the generic capability of the underlying `qwen2.5-coder:7b-instruct-q4_K_M` language model or the twelve-agent orchestration topology alone.

The ablation design employs three experimentally controlled variants of the Noesis system that are identical in every respect except for the configuration of the C3 memory subsystem. All three variants share the same twelve-agent topology, the same PlannerAgent deterministic plan construction, the same Vidya coding-agent prompting strategy, the same Kriyakari SIGNOFF adjudicating heuristic, the same `qwen2.5-coder:7b-instruct-q4_K_M` language model, the same laptop-first hardware platform, and the same fixed random seed of 42 across all three runs per task. **Variant A - No Memory** completely disables the C3 architecture and substitutes a flat BM25-only retrieval mechanism that queries the raw document corpus directly without any tiered promotion, contextual buffering, or meta-memory reflective reasoning; this variant operationalises the null hypothesis that any form of retrieval, regardless of architectural sophistication, is sufficient to achieve the observed SE50 performance. **Variant B - T1-T3 Only** enables the first three volatile memory tiers (Samjnana, Smrti, and Citta) but disables the persistent tiers (Prajnana, Vijnana, and Dhyana), thereby isolating the contribution of within-session working-memory buffering from the cross-session semantic and procedural knowledge accumulation that characterises the full architecture. **Variant C - Full 6-Tier C3** enables the complete six-tier Sanskrit-engineered memory system with the default promotion policy and represents the production configuration of the Noesis system as described in Chapters 3 and 5.

All three variants are evaluated on the identical SE50 corpus of 50 tasks x 3 runs = 150 observations used for the primary analysis of section 6.1, yielding a fully paired experimental design where every (task, run) combination is observed under all three memory variants. Paired designs are statistically more powerful than independent-groups designs because they eliminate between-task heterogeneity as a source of residual variance; the paired McNemar test reported in section 6.5 exploits this property directly to assess the significance of the Variant A versus Variant C difference.

## 6.5 Statistical Significance Analysis

All quantitative results reported in this chapter were computed using the `noesis.benchmarks.stats` module, a purpose-built Python statistics library that implements the complete suite of estimators and inferential procedures required for reproducible code-generation benchmark analysis. The module exports five canonical functions: `wilson_ci(k, n, confidence=0.95)` for score-method binomial confidence intervals, `pass_at_k(correct_per_problem, k)` for the Chen et al. unbiased pass@k estimator, `mcnemar_test(paired_table, exact=True)` for the paired binary homogeneity test, `bootstrap_pass_at_1(results, n_resamples=10000, seed=42)` for nonparametric bootstrap resampling of the pass@1 statistic, and `summary_report(df, group_cols)` that composes the preceding four functions into a single callable that mirrors the column schema of the CSV tables presented in section 6.1 through section 6.4. The module is instrumented with a deterministic seeded random number generator and is covered by a unit-test suite (`backend/tests/unit/test_bench_stats.py`) that validates each exported function against hand-computed reference values for edge cases including k = 0, k = n, and n = 1, guaranteeing numerical correctness of the reported statistics.

### 6.5.1 McNemar's Paired Test on SE50 Variant A vs Variant C

To assess the statistical significance of the C3 ablation effect reported in section 6.4, McNemar's test for paired binary data [21] is applied to the 150 paired (Variant A, Variant C) pass/fail decisions generated by the fully matched SE50 experimental design. McNemar's test is the appropriate inferential procedure for this setting because it explicitly accounts for the paired structure of the data: each of the 150 (task, run) combinations is measured under both the no-memory condition (Variant A) and the full-C3 condition (Variant C), yielding a 2 x 2 contingency table whose off-diagonal cells b and c count the number of discordant pairs in which Variant A passed but Variant C failed (b) and vice versa (c). Under the null hypothesis H0 that the two variants are identically distributed, the test statistic `(b - c)^2 / (b + c)` follows an asymptotic chi-squared distribution with one degree of freedom; for small discordant counts (b + c < 25), the exact binomial variant of the test is preferred and is implemented as the default in `noesis.benchmarks.stats.mcnemar_test`.

The computed McNemar chi-squared statistic is `25.037 (DRYRUN_LABELED - laptop dry-run placeholder; swap with real W7 --full overnight qwen/deepseek adaptive run numbers when available)` with an associated two-tailed p-value of `2.812e-07 (DRYRUN_LABELED - laptop dry-run placeholder; swap with real W7 --full overnight qwen/deepseek adaptive run numbers when available)`. If this p-value is less than the conventional a = 0.05 significance threshold, then the null hypothesis of identical pass-rate distributions between Variant A and Variant C is rejected, and one may conclude that the observed 12-percentage-point C3 lift is statistically distinguishable from zero at the 95% confidence level. If the p-value exceeds 0.05, then a cautious interpretation would be that while the point estimate of the C3 lift is consistent with the novelty claim, the available sample size of 150 paired observations provides insufficient evidence to rule out sampling fluctuation as a competing explanation; in that case, the bootstrap interval reported below would still permit a bounded confidence statement about the plausible magnitude of the C3 effect.

### 6.5.2 Bootstrap Resampling for Confidence-Interval Stability

As a complement to the parametric Wilson score intervals reported in Tables 2, 3, and 5, nonparametric bootstrap resampling with 10,000 replicates was employed to assess the sampling stability of all aggregate pass@1 estimates [22]. The bootstrap procedure operates by constructing 10,000 synthetic datasets of size 150 for SE50 (164 for HumanEval, 500 for MBPP) by sampling with replacement from the original empirical pass/fail vector, computing the pass@1 proportion for each synthetic dataset, and then extracting the 2.5th and 97.5th percentiles of the resulting 10,000-element bootstrap distribution to form a percentile-method 95% confidence interval. Bootstrap intervals are asymptotically equivalent to the Wilson intervals for well-behaved binomial proportions but possess the practical advantage that they may be applied straightforwardly to derived statistics-such as the C3 d = Variant C - Variant A lift reported in section 6.4-for which no closed-form parametric interval estimator exists.

Concordance between the Wilson interval and the bootstrap interval at 3 or more significant digits is used as a numerical validity check on the `noesis.benchmarks.stats` module implementation. Any systematic discrepancy exceeding two percentage points between the two interval methods would trigger a diagnostic review of the bootstrap resampling logic, the Wilson score computation, or the underlying data pipeline; conversely, close agreement between the two methods increases confidence that the reported interval estimates are not artefacts of a specific parametric assumption. The 10,000-resample configuration was selected after a pilot power analysis demonstrated that stabilising the 2.5th percentile of the bootstrap distribution to within +/-0.5 percentage points required approximately 8,000 resamples; 10,000 resamples were therefore adopted as a conservative default that adds modest computational overhead on a laptop-first platform (approximately 90 seconds of wall-clock time on the reference hardware) while guaranteeing adequate Monte Carlo standard error for the interval endpoints.

## 6.6 Threats to Validity

A rigorous interpretation of the empirical results presented in this chapter requires explicit acknowledgement of the methodological limitations that bound the scope and strength of the inferences that may be drawn from the data. Following the taxonomy proposed by Shadish, Cook, and Campbell (2002), threats to validity are organised into four categories-internal validity, external validity, construct validity, and statistical conclusion validity-each discussed below with specific reference to the Noesis evaluation design, together with the mitigation strategies that were adopted to attenuate each threat where feasible.

### 6.6.1 Internal Validity Threats

Internal validity concerns the extent to which the observed covariation between the independent variables (memory architecture variant, benchmark corpus, difficulty tier) and the dependent variables (pass@1, runtime, memory-promotion count) reflects a genuine causal relationship rather than the operation of confounding extraneous variables. The first and most consequential internal validity threat arises from the deterministic seeded plan construction implemented by the PlannerAgent module. Because the PlannerAgent is a rule-based finite-state machine rather than an LLM-native planner, its decomposition of each SE50 task into a linear sequence of Sanskrit-agent invocation steps is fully reproducible across all three runs of a given task and across all three variants of the ablation study. While this determinism is desirable from the perspective of reproducibility, it introduces the risk that the specific plan graph overfits to the structural idiosyncrasies of the SE50 corpus, inflating the apparent pass@1 relative to what would be observed under a stochastic LLM-native planner that sampled alternative decompositions per run. A second internal validity threat is the single-model evaluation design: only `qwen2.5-coder:7b-instruct-q4_K_M` was deployed as the generation and evaluation engine, leaving unknown the extent to which the C3 architecture lift would generalise to other code-specialised models such as CodeLlama 7B, StarCoder2 7B, or DeepSeek-Coder V2 7B. A third internal validity threat is the limited number of runs per task (k = 3): while three runs are sufficient for Wilson interval estimation, they provide limited statistical power for detecting run-to-run variance components or for estimating pass@k metrics for k >= 5.

### 6.6.2 External Validity Threats

External validity concerns the degree to which the results may be generalised beyond the specific experimental conditions under which they were collected. The most salient external validity threat is the limited size and provenance of the SE50 corpus: all 50 tasks were authored by UPES B.Tech. computer science students under supervision of the thesis investigator, and the corpus is therefore orders of magnitude smaller than community-standard benchmarks such as SWE-bench Lite, which comprises more than 2,000 real-world GitHub issues drawn from 12 popular Python repositories. While the five-category stratification of SE50 provides nominal coverage of the software engineering lifecycle, the absence of tasks requiring cross-repository navigation, long-lived pull-request discussions, or adherence to idiosyncratic project-specific coding conventions means that the SE50 results cannot be extrapolated directly to the SWE-bench difficulty regime without a separate bridging study. A second external validity threat is the laptop-first single-platform evaluation: all experiments reported in this chapter were executed on a single RTX 40xx-series laptop configuration. The cross-platform performance of Noesis on NVIDIA Jetson AGX Orin edge hardware is deferred to Work Package 16 of the project schedule and is therefore unavailable at the time of thesis submission; given the substantially different memory bandwidth and CPU-core topology of the Jetson platform relative to a consumer laptop, it is an open empirical question whether the C3 memory architecture lift observed on the reference hardware would be preserved on an edge-deployed configuration.

### 6.6.3 Construct Validity Threats

Construct validity concerns whether the operationalised dependent variables faithfully measure the theoretical constructs of interest. The principal construct validity threat in this evaluation is the Kriyakari SIGNOFF heuristic as the operational definition of a task pass. While the SIGNOFF heuristic automates the gatekeeping function of a human lead engineer by conjunctively evaluating compilation, testing, and accept-criteria predicates, it is not a 100% gold-standard human rater: there exists the possibility that a task could be judged SIGNOFF-PASS by the heuristic yet fail a nuanced human review on stylistic grounds, maintainability, or adherence to implicit project norms; conversely, a task could be judged SIGNOFF-FAIL due to a brittle accept-criteria predicate that is technically satisfied but semantically misinterpreted by the agent. The inter-rater reliability (Cohen's kappa) between the Kriyakari SIGNOFF heuristic and a panel of independent human raters was not measured as part of the present evaluation and is therefore reported as an unknown quantity. A secondary construct validity threat is the operationalisation of the C3 memory contribution exclusively through the pass@1 and runtime metrics; additional constructs such as code readability, agent plan efficiency, and memory-promotion alignment with task-phase transitions are not directly quantified in the current design, leaving implicit the mechanism by which the six-tier architecture translates into improved end-to-end task performance.

### 6.6.4 Mitigation Strategies

The preceding validity threats are attenuated through several methodological choices that are explicitly documented throughout this chapter. First, the combination of three independent runs per task with the nonparametric 10,000-resample bootstrap procedure provides bounds on the sampling variability of all aggregate pass@1 estimates, ensuring that even if the point estimates are biased by corpus idiosyncrasies, the interval estimates characterise the plausible range of the true parameter. Second, the McNemar paired significance test on the 150 matched Variant A / Variant C observations provides a formal inferential guard against interpreting the C3 ablation lift as a Type I sampling error. Third, the inclusion of two canonical community benchmarks-HumanEval 164 and MBPP 500-alongside the custom SE50 corpus permits cross-benchmark triangulation that would detect if the SE50 results were idiosyncratically inflated by the UPES-authored corpus design. Fourth, every quantitative computation is delegated to the open-source `noesis.benchmarks.stats` module with a dedicated unit-test suite, eliminating manual calculation error as a confound and enabling independent replication of all reported statistics by third-party investigators. Notwithstanding these mitigations, the results of this evaluation are most appropriately interpreted as a laptop-first, single-model, purpose-built-corpus demonstration of the Noesis architecture's viability, rather than a definitive general-purpose characterisation of Sanskrit-engineered multi-agent systems across all deployment regimes and all code-generation tasks.
