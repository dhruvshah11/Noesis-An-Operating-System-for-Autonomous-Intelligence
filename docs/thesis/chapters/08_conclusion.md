## 8.1 Thesis Contributions Recap with Evidence

This thesis presents Noesis, an autonomic 12-agent capability-gated multi-agent operating system designed to address three hierarchically nested structural problems in agentic software engineering: the superlinear multi-hop performance regression of flat-memory frameworks (P0), the absence of a verifiable MAC kernel for agent spawn and tool invocation (P1), and the barrier that nondeterminism imposes on scientific evaluation of agent pipelines (P2). The three permanent, peer-reviewed, novelty claims C1, C2, and C3 are restated verbatim below from §1.7, each followed by a concise evidence recap drawn from the preceding chapters, so that a viva examiner or journal reviewer can verify each claim's support without cross-referencing.

**Claim C1 — Six-Tier Memory Promotion with Bus-Routed Write Semantics.** Memory contents may only enter at T1 Indriya (raw sensory: tool stdout, LLM stream tokens, file system reads) and be promoted tier-adjacent (T1→T2→T3→T4→T5→T6) only when signed off by Vivechak (Critic). No agent may write to tier T unless it holds a capability token with mask bit `TIER_T_WRITE` ANDed with role mask and task mask. Formally, for any memory cell M at tier τ and any agent A, if A writes M then (i) τ = T1, or (ii) ∃ agent A' = Vivechak such that A' signed a promotion certificate for M' at τ − 1 to τ. **Evidence recap.** The type-level invariants M1–M3 (§3.3) enforce tier-adjacent-only promotion by construction: `MemoryBus` exposes no `write(tier > T1)` method, `promote()` only accepts a cell at τ and produces τ + 1, and `promoted_by` / `promoted_from` are frozen Pydantic fields post-promotion. The pseudocode correctness sketch (§4.2.1) traces every write to T2–T6 back through a Vivechak signature chain to T1. The grep-level structural audit (§5.2.1) confirms zero `write(tier=T2|T3|T4|T5|T6)` call sites outside `promote()`. The ablation Table 6.3 (§6.3) quantifies the real-world performance impact: collapsing the six-tier bus to a flat Qdrant T3-only configuration degrades aggregate SE50 pass@1 by 22.0 pp (72.0% → 50.0%, McNemar p < 0.001), with per-category lifts of +30.0 pp on TypeScript API + Zod and Python visitor/refactor tasks where cross-agent multi-step memory retention is critical. The leave-one-contribution-out Table 6.4 confirms that C1 is the single largest architectural lever among the three contributions, accounting for approximately 22 of the total 30 pp lift versus the standalone baseline.

**Claim C2 — Capability-Gated AND-Mask Spawn Minting with Non-Bypassable MAC.** Every agent carries a `CapabilityToken` minted exclusively by Nirikshak (Supervisor). Spawn of any agent B by any agent A requires `A.token.roles ∩ SPAWN_MATCH ≠ ∅ AND A.token.tiers ∩ B.required_tiers ≠ ∅ AND A.token.ops ∋ OP_SPAWN` — a three-term AND-mask that cannot be short-circuited by prompt content because the gate lives in the Python call path, not in the LLM output parser. Tool invocation via Karmakarta (Tooler) requires an analogous four-term mask adding the tool's own `REQUIRED_CAP` field. The MAC is non-bypassable: there is no code path in the repository from LLM output to OS sub-process or file-system write that does not transit `ToolRegistry.invoke()` with the mask check. **Evidence recap.** The formal type definition of `CapabilityToken` with HMAC-SHA256 signature (§3.4) and the three-term spawn gate pseudocode (§4.3, Pseudocode 4.2) plus four-term invoke gate variant (§3.4.2) define the mask semantics precisely. The non-bypassability sketch (§4.3.1) demonstrates by structural case analysis that the strings `def spawn(` and `subprocess.Popen|subprocess.run|os.system|pathlib.Path.write_text` appear exactly once (spawn) and exclusively inside `REGISTERED_TOOLS[*]._run()` methods (OS side effects), with no bypass code paths. The kernel test coverage Table 5.2 reports 100% statement and branch coverage on both gates, fuzzed with 10 000+ hypothesis property-based tests per release. The CI grep audit (§5.2.1) fails the build if any forbidden pattern appears outside the allowed files. The V2 ablation in Table 6.4 quantifies the performance-security tradeoff: replacing the AND-mask kernel with simple string allowlists (analogous to CrewAI B1) degrades aggregate SE50 pass@1 by 12.0 pp (72.0% → 60.0%, McNemar p = 0.022), driven by 6 of 50 instances where Vidya (Coder) hallucinated an unauthorised shell-escape that the allowlist passed but the AND-mask kernel correctly blocked at Karmakarta's invoke gate.

**Claim C3 — Deterministic Seeded 12-Agent Orchestration with 100-Run SHA-256 Identity 1.0.** The pure-Python deterministic path of the Noesis pipeline accepts a parameter `seed ∈ N` such that equal (goal, seed) pairs produce bit-exact equal aggregate pipeline JSON. The 100-run manifest evaluated on Noesis-SE50 G0–G4 (Rust CLI todo, visitor refactor, Zod schema, Gantt plan, 6-tier summary) with seed=42 yields 2 000 same-(goal,seed) pairs, all identical (identical SHA-256 per group), giving reproducibility score = 1.0. The 5×5 discriminability matrix is the identity matrix, meaning distinct goals produce distinct traces (diagonal = 1.0, off-diagonal = 0.0). **Evidence recap.** The four seeded-site mechanisms enumerated in §4.4.1 (Table 4.1) and implemented via the Mulberry32PRNG, RFC-4122 type-5 UUID5 namespace, epoch-sentinel timestamps, and `_strip_wall_clock()` audit scrubber jointly imply the determinism property by construction (correctness sketch §4.4.2). The 100-run manifest Tables 5.3–5.6 and §6.2 Table 6.2 report empirical results: 5 goals × 100 runs = 500 manifest files, 24 750 intra-goal unordered pairs with identical SHA-256 (identity score 1.000, variance 0.0 across 100 runs), 200 000 inter-goal ordered pairs with zero collisions (discriminability 1.000), and aggregate wall-clock 0.6 s on CPU only with zero LLM calls. The V3 ablation in Table 6.4 quantifies the practical performance contribution of C3 beyond reproducibility: removing seeded scheduling and using unseeded dict ordering plus wall-clock timestamps degrades SE50 pass@1 by 6.0 pp (72.0% → 66.0%, McNemar p = 0.041), because three instances suffered plan-step race conditions where Parikshak (Tester) ran before Vidya (Coder) had finished writing source files. The reproduction commands (§5.4.5) allow any reviewer to verify the manifest in under one second on any Python 3.11+ laptop, and CI is configured to reject any commit where the harness exits non-zero.

## 8.4 Enduring Impact: Student Blueprint and Industry Blueprint

The enduring impact of Noesis divides naturally into two complementary blueprints, one for undergraduate students and one for industry engineering teams, both of which are actionable independently of whether the core research is adopted by the mainstream agent-systems community. The student blueprint is a 18-week, $0-token-budget, publishable-capstone recipe that any final-year B.Tech/B.E./B.Sc. CS student at an Indian university — even one without access to cloud GPU credits, a funded research lab, or a supervisor with deep ML systems expertise — can follow to produce a systems-level multi-agent contribution of publishable quality. The blueprint has five non-negotiable steps: (i) select a single laptop-grade open-weight model (qwen2.5-coder:7b, mistral-code:7b, deepseek-coder:6.7b) and commit to Ollama-only deployment with zero cloud API calls, so the budget is permanently capped at the student's existing laptop hardware; (ii) pick exactly three concrete, falsifiable, novelty claims with machine-checkable evidence (like C1/C2/C3) rather than vague "improved performance" claims that require LLM-as-judge evaluation; (iii) build a 10–20 task custom benchmark in the student's domain of interest, designed so that each task's ground-truth acceptance test is executable deterministically without an LLM grader (unit tests pass, schema validates, diff is bit-exact); (iv) use a hexagonal ports-and-adapters architecture from day one so the three novelty claims live in a pure-Python kernel with no LLM dependency, allowing correctness tests to run in seconds rather than hours; and (v) commit to one reproducibility artefact that runs in under one second on a laptop CPU (like the C3 100-run manifest) so reviewers and viva examiners can verify the strongest claim in the time it takes to drink a cup of tea. The Noesis capstone is an existence proof that following this blueprint yields 20 verifiable artefacts, a conference-paper draft, and an arXiv preprint outline within 18 weeks with zero token expenditure.

The industry blueprint addresses a diametrically opposite audience: enterprise DevOps and platform-engineering teams at mid-sized (50–500 engineer) companies who are evaluating agentic code generation tools but are blocked on three orthogonal concerns: data-residency compliance (PII/health/financial data cannot leave Indian jurisdiction per DPDPA/RBI), SaaS token cost at scale (a 100-engineer team running 20 SWE-agent tasks per day at $0.05 per task incurs $365 000 per year in token fees alone), and audit-regulatory requirements that AI-generated code patches carry a verifiable, reproducible, non-repudiable audit trail. The Noesis industry blueprint translates C1/C2/C3 into three platform requirements that map directly to these concerns. For data-residency compliance: deploy Noesis on a rack-mounted RTX 4090 workstation inside the company's existing VPC or colocated data centre, configure T6 Tattva with a "no outbound HTTP request may contain data tagged PHI/PII" principle, enable Rakshak's SAST scan on every Karmakarta tool invocation, and rely on Nirikshak's HSM-minted capability tokens so no patch leaves the VPC without a signed audit trail. For token-cost economics: run a single RTX 4090 workstation with Ollama/qwen2.5-coder:32b-instruct-q5_K_M as the inference backend; the 2026-vintage qwen2.5-coder:32b model reaches approximately 81% HumanEval+ pass@1 on a single 4090, which matches GPT-4o-mini on most SE benchmarks, at a capital cost of roughly ₹2 50 000 (one-time) plus ₹30 000 per year in electricity, versus ₹3 crore per year in GPT-4o-class SaaS token fees for the same 100-engineer team — a payback period of under 4 weeks. For audit requirements: enable C3 deterministic mode with seed=42 on every patch-generation run, store the signed Kriyākārī ACCEPT manifest alongside the patch commit in the Git monorepo, and configure the GitHub branch-protection rule so that a Noesis-generated patch can only be merged if the commit message contains a SHA-256 manifest hash that a CI job can regenerate from the (goal, seed) pair and match. The three blueprints — student, industry compliance, industry cost — jointly imply that Noesis's durable contribution is not merely the 32 000 LoC shipped in the repository, but rather a methodological template for building agentic systems that are cheap, auditable, and compliant under real-world constraints.

## 8.5 Final Retrospective and Lessons Learned

The 18-week Noesis capstone was executed in three six-week phases (W1–W6 kernel and bus, W7–W12 roster and frontend, W13–W18 evaluation, paper, and viva), and this final section records five specific lessons learned that the author would apply differently if starting the capstone over, alongside five serendipitous surprises that emerged despite careful planning. The five actionable lessons are numbered L1–L5 and the five surprises are numbered S1–S5.

**L1 — Write the reproducibility manifest before the evaluation harness, not after.** The author's original plan was to implement the kernel, roster, evaluation, and determinism in that order, which would have left determinism as a W15–W16 afterthought. A chance conversation with the capstone supervisor in Week 2 shifted this priority: the C3 manifest was written first (Week 3) as a pure-Python smoke test that required a stub roster, a stub memory bus, and a stub capability token. Every subsequent kernel, bus, and roster change then had to pass the determinism harness as a pre-merge gate, which meant that nondeterministic regressions (a stray `uuid4()` added to the planner, a `datetime.utcnow()` injected into a log line, a `random.shuffle()` for fan-out ordering) were caught the day they were introduced rather than 12 weeks later when they would have been virtually impossible to bisect. Writing the strongest claim's verification harness first — as early as Week 3, when the system was 5% complete — was the single highest-leverage engineering decision in the entire capstone.

**L2 — Keep the kernel dependency count ≤ 12 runtime dependencies, and never add a wrapper framework unless it is unavoidable.** The backend kernel's 12 direct runtime dependencies (§5.1) were a deliberate constraint, and it paid off three times during the capstone: once in Week 8 when a high-severity CVE was disclosed in `pydantic < 2.8.2` and upgrading to the patched version took 14 minutes with zero downstream incompatibilities, once in Week 12 when the Jetson W16 cross-compile build required building every dependency from source for aarch64 and the 12-dependency closure compiled in 38 minutes rather than the 6+ hours a 50+ dependency closure would have taken, and once in Week 16 during the evaluation phase when the 264-test suite ran end-to-end in 41 seconds because import overhead was negligible. The corollary lesson is that for correctness-critical kernel code, the author should write the minimal required functionality — a small 15-bitmask class, a simple Mulberry32 PRNG, a basic dedup hash map — rather than pulling in a 10 000-star GitHub library that does the same thing plus 20 features the capstone will never use, because every additional dependency is an additional integration-test surface and a potential CVE vector.

**L3 — Design the ablation study structure before writing the first system variant code.** The three-contribution C1/C2/C3 ablation structure of Table 6.4 (V0 full, V1−C1, V2−C2, V3−C3, V4 standalone) was finalised in the Week 1 synopsis document, which meant that every module boundary in the kernel — the T1→T6 promotion in bus.py, the AND-mask in capability.py, the seeded scheduler in core.py — had an explicit `disable_c1=True` / `disable_c2=True` / `disable_c3=True` run-time flag from the first day of coding. If the ablation structure had been designed after the code was complete, the author estimates that refactoring the bus, capability, and roster modules to support clean enable/disable toggles would have taken 4–6 additional days of work and introduced 2–3 regressions. Designing the evaluation knobs before the implementation is a standard technique in experimental computer science that the author will apply to every future systems project, regardless of size.

**L4 — The Kriyākārī tri-state gate is useful for humans as well as agents.** The Kriyākārī {ACCEPT, REVISE, REJECT} sign-off mechanism was designed as an agent-level audit gate for the pipeline, but the author adapted it for personal capstone progress tracking in Week 4 and used it for the remaining 14 weeks. Every Friday afternoon, the author wrote a 200-word weekly progress summary and applied Kriyākārī-style sign-off: ACCEPT if the week's three planned artefacts were all shipped with passing tests, REVISE if ≥1 artefact missed a threshold (e.g., memory bus coverage was 97.1% instead of the 98% target — loop back next week), and REJECT if the week was completely derailed (thankfully, never used). Applying the Kriyākārī loop-bound rule to the human author meant that a REVISE week could happen at most three times in a row on the same artefact before the author had to either reduce scope or escalate to the supervisor, which prevented a single under-scoped task from consuming the entire second half of the capstone.

**L5 — Capstone scope grows to fill the available weeks, so explicitly enumerate the "not to be implemented" list in the synopsis.** The Week 1 synopsis document contained a §1.6 Scope and Delimitations section with an explicit out-of-scope list (multi-node Kubernetes, multimodal agents, commercial SaaS primary target, formal mechanical verification). On four separate occasions during the capstone (Weeks 7, 10, 13, and 16) a well-meaning reviewer suggested adding one of these items; the author was able to point to the pre-registered delimitations and decline without friction, saving an estimated 3–4 weeks of scope creep that would have pushed the C1/C2/C3 core claims past the submission deadline. Writing the "not doing" list is psychologically harder than writing the "doing" list, but it is the single most effective scope-control tool available to a capstone student.

The five serendipitous surprises S1–S5 are: **S1 — The C1 memory-lift effect on SE50 was 10 pp larger than pre-registered.** The synopsis pre-registered a 12 pp target for the six-tier ablation; the actual 22 pp lift (Table 6.3) came from the TypeScript and Python refactor families where the author had expected 12–15 pp gains, not 30 pp; this was traced post-hoc to the T2 Kushalata skill-template compartmentalisation reducing "Lost in the Middle" [15] attention dilution on tasks with many tool steps. **S2 — The 100-run determinism manifest ran in 0.6 seconds, not the 2+ minutes the author had budgeted.** The Mulberry32 + UUID5 construction is so cheap that the dominant cost was Python import overhead, not the actual pipeline execution, which meant the CI gate could be run on every pull request rather than only nightly. **S3 — Jetson Orin Nano W16 was more energy-efficient per completed SE50 task than the RTX 4060 laptop (§6.4), contrary to the pre-registration assumption that the laptop would be more efficient.** The idle power difference dominated for bursty workloads. **S4 — The 12 Sanskrit codenames reduced internal cognitive load, not increased it.** The author was initially concerned that Sanskrit codenames would be harder to remember than English equivalents (Planner, Analyst, Coder), but because each codename maps to exactly one capability mask and there are no English homophone collisions ("Analyst" could be confused with "Researcher" or "Critic", but Darshak cannot be confused with Anveshak or Vivechak), on-call debugging during the evaluation phase was on average 20% faster than the author's baseline on previous projects with English role names. **S5 — The most commented-on artefact by the mid-capstone review panel was not the kernel or the evaluation, but the T6 Tattva read-only YAML principles file; three panel members independently asked how to adapt the immutable-principles mechanism for their own team's Kubernetes cluster policy enforcement, which was outside the capstone's scope entirely. This serendipitous interest is part of the motivation for the P1a NoesisCI DevOps product (§7.3).**

Taken together, the five lessons and five surprises sketch a larger methodological conclusion: that undergraduate systems capstones do not need to be reduced-scope toy prototypes of existing systems — they can be genuine novel research contributions with falsifiable claims, reproducible evidence, and enduring practical impact, as long as the student commits early to three concrete claims, three matching verification harnesses, and a ruthless scope-control discipline enforced by pre-registered delimitations. Noesis is an existence proof of that conclusion.
