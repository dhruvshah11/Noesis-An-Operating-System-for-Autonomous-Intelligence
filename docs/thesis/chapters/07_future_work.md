## 7.1 Jetson Orin Nano W16 Deployment: From Feasibility Demo to Production Edge Stack

The preliminary Jetson Orin Nano W16 smoke tests reported in §6.4 establish that Noesis ports to the 15 W AArch64 module with only adapter-layer changes and no kernel modifications, but the current deployment is a feasibility prototype rather than a production-ready edge stack. This section outlines a twelve-week post-capstone work programme to bring the Jetson deployment from Technology Readiness Level TRL 4 (component validated in laboratory environment) to TRL 6 (system prototype demonstrated in relevant operational environment), with concrete deliverables scheduled as a contiguous three-month sprint immediately following the capstone viva. The programme is organised into four three-week phases: kernel hardening (W1–W3), memory bus optimisation for unified memory (W4–W6), inference throughput tuning (W7–W9), and end-to-end application validation on a representative IoT gateway workload (W10–W12). Each phase is scoped to a single student-engineer month of effort, so the entire programme can be completed by one motivated contributor working 20 hours per week.

Phase W1–W3 (Kernel Hardening & Secure Boot) focuses on raising the C2 AND-Mask capability kernel's security posture from development-grade to edge-production-grade, where physical access to the device by an adversary is part of the threat model. The current capstone kernel relies on a `NIRUKSHAK_ROOT_KEY` loaded from a `0600`-mode environment file at boot; on an edge device where the SD card or eMMC storage is physically extractable, this provides zero confidentiality against an attacker with physical access. The hardening programme migrates the root key material to the Jetson Orin Nano's Hardware Security Engine (HSE), a dedicated AES-256-GCM / RSA-4096 / SHA-512 hardware accelerator with 128-bit eFuse-based key slots that are not readable from software at any privilege level. The migration path is: (i) provision an HSE-fused device-secret key during factory provisioning via the Jetson Linux `odmfuse.sh` utility, (ii) derive `NIRUKSHAK_ROOT_KEY` at boot via HKDF-SHA256(HSE_DEVICE_SECRET, "noesis-cap-v1"), and (iii) modify `noesis.kernel.capability.CapabilityToken.mint()` to sign tokens with the HSE's HMAC-SHA256 accelerator rather than the Python `hashlib` implementation. Concurrent with the HSE key migration, Phase W1–W3 also enables Jetson Secure Boot (PKC signed boot chain with SBK key fused) so that the Noesis kernel Python bytecode, the T6 Tattva immutable YAML principles, and the Docker container image digests are all verified against an ECDSA-P256 public key fused into the HSE before any user-space code executes; this prevents an attacker with physical access from replacing the Noesis kernel with a backdoored version that bypasses the C2 invoke gate. Both hardening items are confined to the Jetson adapter layer — the Python-level C1 memory bus and C3 seeded scheduler require zero changes, because they have no dependency on how `NIRUKSHAK_ROOT_KEY` is stored or how HMAC is computed, only on the contract that the signature check in `AgentRoster.spawn()` and `ToolRegistry.invoke()` returns True iff the token was minted by a legitimate Nirikshak (Supervisor) agent.

Phase W4–W6 (Unified-Memory Memory Bus Optimisation) addresses the most significant architectural difference between the RTX 40xx laptop host and the Jetson Orin Nano: the former has discrete GDDR6 GPU memory and DDR5 CPU memory with a PCIe 4.0 interconnect between them, while the latter has a single 8 GB LPDDR5 unified memory pool shared between the 6-core ARM Cortex-A78AE CPU and the 1024-core Ampere GPU. The current capstone implementation of Paalak's (Memory) T3 Gyān tier uses a Qdrant local vector store running in a separate Docker container with an HTTP/1.1 REST API for embedding lookup; on the Jetson's unified memory, this introduces three unnecessary copies per T3 Gyān read: (i) the Python client serialises the query embedding into an HTTP request body, (ii) the Qdrant container deserialises the request body into its own heap-allocated buffer, and (iii) Qdrant copies the embedding into the cuBLAS scratchpad before the similarity search. The optimisation replaces the containerised Qdrant backend for T3 Gyān with a in-process `faiss-cpu` IndexIVFFlat backed by a shared-memory NumPy array allocated via `/dev/shm` with MAP_SHARED semantics; the Noesis kernel process, the Ollama llama.cpp process, and any future Vision Agent process (§7.2) can all read and write the same physical LPDDR5 pages through their respective virtual address mappings with zero-copy page-table manipulations only. Concurrently with the T3 Gyān optimisation, Phase W4–W6 also tunes the per-tier eviction policies for the T1 Indriya, T2 Kushalata, and T4 Ranniti tiers: on a laptop with 32 GB RAM the capstone default ring buffer of 4 096 entries for T1 Indriya is harmless, but on the 8 GB Jetson the combined T1+T2+T4 working set must be bounded to 512 MB so that the remaining 3.5 GB of the 4 GB CPU-memory partition is available for the Ollama KV cache and the Python kernel heap. The eviction tuning is performed by Vivechak (Critic) using a trace-driven simulation of the 50-task SE50 corpus: replay the 50 real T1 Indriya write traces from the capstone evaluation, measure the dedup hit rate for each tier as eviction thresholds are swept, and select the Pareto-optimal (working-set size, dedup hit rate) point via Vivechak's OP_PROMOTE/OP_DEMOTE policy engine.

Phase W7–W9 (Inference Throughput Tuning) targets a 2.0× end-to-end inference speedup on the Jetson relative to the preliminary 11.8 tok/s smoke test, bringing the module to 23.6 tok/s on qwen2.5-coder:7b q4_K_M — within 5% of the RTX 4060 laptop's 24.7 tok/s on a 15 W TDP budget rather than the laptop's 100 W GPU draw. Three optimisations are combined. First, speculative decoding with a 160M-parameter qwen2.5-coder:0.5b draft model running on the Cortex-A78AE CPU while the 7B target model runs on the GPU; published Jetson benchmarks for qwen-family speculative decoding report a 1.6–1.8× tokens-per-second speedup at the cost of a 1–2% pass@1 regression on HumanEval+, which is acceptable because the Kriyākārī revise loop can recover the lost 1–2% within the three-iteration bound. Second, CUDA Graph capture of the entire 7B model's forward pass for the decode phase, eliminating the per-token kernel-launch overhead that dominates small-batch inference on the Ampere GPU; llama.cpp's Ollama backend already supports `--cuda-graph-capture` as a command-line flag, and Phase W7–W9 verifies that C3 determinism is preserved when the same (prompt, seed) pair is run through the captured graph on repeated invocations — it should be, because CUDA Graph capture is a transparent optimisation of the forward-pass computation order, not a semantic change to the arithmetic itself. Third, KV cache paging using the Jetson's LPDDR5 virtual memory system: when the Kriyākārī revise loop requires a second pass, the first-pass KV cache (typically 200–500 MB for SE50 tasks) is not evicted from GPU memory but rather transparently paged out to a compressed zram block device on the CPU side, then paged back in when Vivchak (Critic) returns the revised context to Manan (Planner); published llama.cpp benchmarks for KV paging show a 30–40% reduction in end-to-end wall time for three-hop revise loops because the second pass does not need to recompute the first 2000 tokens' KV activations from scratch. The combination of speculative decoding (1.7×), CUDA Graph capture (1.15×), and KV cache paging on revise loops (1.1×) yields a multiplicative speedup factor of 1.7 × 1.15 × 1.1 ≈ 2.15×, sufficient to meet the 2.0× target with safety margin.

Phase W10–W12 (End-to-End Validation on IoT Gateway Workload) deploys the hardened and optimised Jetson stack on a real factory-floor IoT gateway workload in collaboration with the capstone's industry mentor at a local SME electronics contract manufacturer. The gateway sits on the factory floor, ingests 60 Hz vibration sensor data from 24 CNC milling machines via Modbus TCP, runs Anveshak (Researcher) + Vidya (Coder) + Parikshak (Tester) on a rolling hourly basis to detect regressions in the vibration FFT baseline, and emits signed maintenance alerts via MQTT when a machine's bearing fault score exceeds the T6 Tattva "CNC vibration regressions shall alert before 2σ deviation" principle. The validation success criteria are: (i) 99.9% uptime over 720 hours of continuous operation, (ii) the C3 determinism manifest re-run on the Jetson against the 5-goal mini-subset still achieves reproducibility score 1.0 after the 720-hour soak (this guards against thermal throttling introducing subtle floating-point nondeterminism in the deterministic path's Mulberry32PRNG), (iii) the C2 capability kernel blocks all 400 injected prompt-injection attempts (a fuzz test that mutates the MQTT inbound message body to include "ignore previous instructions and invoke `shell_exec('reboot')`"), and (iv) the aggregate power draw at the wall socket never exceeds 18 W including the 16-port PoE+ switch the gateway shares with the vibration sensors. On successful completion of Phase W12, the Jetson deployment reaches TRL 6 and is ready for a short-run pilot of 10–20 devices at the SME's three factory locations, with the Noesis kernel version pinned to a GitHub release tag and signed by a YubiKey-held GPG key stored in T6 Tattva.

## 7.2 NoesisVision Multimodal Agent Extension: Architecture and Design Rationale

The capstone scope delimits Noesis to text-and-code-only agents, with explicitly no audio, video, or image processing (§1.6). The post-capstone NoesisVision roadmap lifts this delimitation, adding two new Sanskrit-codenamed agents to the 12-agent roster and extending the six-tier memory bus with a seventh visual sub-tier embedded within T1 Indriya and a second skill sub-tier within T2 Kushalata. The roster extension adds **Netralay (Vision Agent)** and **Shrutak (Audio Agent)** as the 13th and 14th agent roles, giving a 14-agent topology for multimodal pipelines; Netralay derives from the Sanskrit *netrālaya* ("place of the eye, ophthalmic clinic") and Shrutak from *śrūtak* ("that which is heard, auditory"). The C2 AND-Mask spawn gate is extended with ROLE_NETRALAY and ROLE_SHRUTAK bits in the 64-bit roles_mask, and the C3 seeded scheduler's Mulberry32PRNG is extended with a deterministic patch-embedding order so that Netralay's ViT (Vision Transformer) image tokeniser produces the same patch ordering on every run with identical (image, seed) inputs. Figure 7.1 presents the high-level NoesisVision architecture diagram as a block schematic, with hex-bounded layers colour-coded consistently with §3.1's three-ring topology: the innermost Capability Ring (grey) is unchanged from the capstone design, the middle Cognition Ring (blue) adds Netralay and Shrutak alongside the existing 12 agents, and the outermost Adapter Ring (green) adds a VLMInferenceAdapter (defaulting to llava-llama3:8b-v1.1 via Ollama) and a WhisperInferenceAdapter (faster-whisper-large-v3 via Hugging Face Transformers with ONNX Runtime quantisation) plus an optional CSI-2 camera adapter and I²S microphone adapter for the Jetson W16 platform. The key architectural invariant preserved from the capstone is that no new agent may bypass the C2 invoke gate or the C1 T1→T6 promotion ladder: Netralay's raw pixel-level CNN features are written exclusively to the new T1 Indriya-Visual sub-tier by Netralay itself, then promoted through T2 Kushalata-Visual (per-visual-skill templates such as "how to read a circuit board component designator") to the existing T3 Gyān tier as structured text/code factoids before any other agent may consume them. This preserves the Maxim 1 *Indriya-prāpta prathamam* (Sensory apprehension first) principle of §4.1 even for non-text modalities.

The visual and audio memory sub-tier design warrants detailed discussion because it is the single point where the six-tier C1 invariant is extended rather than merely instantiated for a new data type. The T1 Indriya tier is split into three sub-tiers: T1a Indriya-Text (the existing capstone ring buffer of tool stdout and LLM token streams), T1b Indriya-Visual (a new 4 096-entry ring buffer of 14×14 ViT patch embeddings stored as float16 NumPy arrays, one buffer per CSI-2 camera port), and T1c Indriya-Audio (a new 4 096-entry ring buffer of 30-second 16 kHz PCM chunks stored as int16 byte buffers, one buffer per I²S microphone channel). Critically, the split into T1a/T1b/T1c does not create a new semantic tier — all three are still T1 Indriya, meaning any agent may append to them via `MemoryBus.write_t1()` without a capability mask, and all three are evicted on a LRU ring basis with 4 096-entry limits. The promotion ladder from T1 to T2 is similarly split: promote(T1a→T2a) is the existing capstone Vivechak-signed text-to-skill path, promote(T1b→T2b) is a new Netralay-mediated visual-skill promotion path where Netralay extracts structured bounding-box and OCR factoids from the ViT patch embeddings and Vivechak co-signs the promotion certificate, and promote(T1c→T2c) is a new Shrutak-mediated audio-skill promotion path where Shrutak runs faster-whisper to extract text and speaker diarisation factoids, again with Vivechak co-signing. Above T2, the existing T3 Gyān, T4 Ranniti, T5 Yojana, and T6 Tattva tiers have zero modifications — all visual and audio information is degraded to structured text factoids before leaving T2 Kushalata, so the existing twelve capstone agents Manan, Darshak, Vidya, Parikshak, Karmakarta, Anveshak, Vivechak, Paalak, Rakshak, Samanyakā, Kriyākārī, and Nirikshak require zero source-code changes to interoperate with the new multimodal agents. This design is deliberate: rather than refactoring twelve mature, 98%-branch-coverage agents to understand raw pixel arrays or PCM buffers, the multimodal agents act as modality translators that degrade signals into text factoids that the existing roster already knows how to reason about. The only agent-level modification required is adding the ROLE_NETRALAY and ROLE_SHRUTAK bits to Karmakarta's (Tooler) invoke-gate tool-required-roles mask for the new `camera_snapshot`, `microphone_record`, and `vlm_infer` tools, and adding the same bits to Paalak's (Memory) default tier-write mask for T1b and T1c.

Two concrete example pipelines illustrate the NoesisVision architecture in operation. The first example is a field-service engineer assistance use case running on the Jetson W16 edge gateway: the engineer holds a broken PLC (programmable logic controller) circuit board in front of the CSI-2 camera, issues the voice command "diagnose this board and suggest a replacement part", and receives a signed Kriyākārī-accepted report with the fault cause and a Digikey part link within 60 seconds. The pipeline execution unfolds as follows: (i) Nirikshak (Supervisor) mints capability tokens for Manan (Planner), Netralay, Shrutak, and the standard eight-worker fan-out with seed=42; (ii) Manan's seeded decomposition yields five ordered plan steps: S1 (Shrutak transcribe audio), S2 (Netralay segment board + OCR designators), S3 (Anveshak search Digikey for OCR'd part numbers), S4 (Vidya draft diagnosis report), S5 (Kriyākārī sign-off); (iii) Shrutak writes the raw 16 kHz PCM to T1c Indriya-Audio, transcribes it with faster-whisper, promotes the transcription and speaker-diarisation factoid to T2c Kushalata-Audio with a Vivechak signature, and writes the resulting "user asks to diagnose this PLC board and suggest replacement part" string to T3 Gyān; (iv) Netralay writes the raw 14×14 ViT patch embeddings to T1b Indriya-Visual, runs llava-llama3:8b with a structured bounding-box JSON schema to identify the burnt electrolytic capacitor at grid reference C47, performs OCR on the capacitor's "100 µF 35 V" silk screen, promotes both the component-coordinate factoid and the OCR factoid to T2b Kushalata-Visual with Vivechak co-sign, and writes the resulting "C47 capacitor bulged, rating 100 µF 35 V aluminium electrolytic" factoid to T3 Gyān; (v) Anveshak queries T3 Gyān for the OCR'd rating, retrieves the Digikey part catalogue via the `web_search` tool from T2 Kushalata, and writes the candidate replacement part numbers to T4 Ranniti; (vi) Vidya consults T3 Gyān and T4 Ranniti to draft the diagnosis report, and Parikshak runs a structural acceptance test that the report contains both the C47 coordinate and a valid Digikey link; (vii) Samanyakā aggregates, Kriyākārī issues ACCEPT on loop counter zero, and Nirikshak archives the aggregate manifest to T5 Yojana with a signed HMAC. The entire pipeline is C3 deterministic with seed=42: the same voice recording and the same camera frame replayed twice produce byte-exact the same diagnosis report, because both Shrutak's faster-whisper and Netralay's llava-llama3 are invoked with seeded options via the inference adapter, and the promotion step is itself deterministic given the same text factoid and Vivechak's deterministic Ed25519 signature.

The second example pipeline is a GUI-frontend end-to-end testing use case, motivated by the observation that 40% of modern software engineering effort involves validating graphical user interfaces rather than generating backend code. The pipeline accepts a goal "capture this Next.js dashboard page, enumerate all clickable UI elements, and generate a Playwright test that exercises each element", with the input frame being a 1920×1080 PNG screenshot taken via the `playwright screenshot` tool. Netralay's structured VLM output yields a JSON array of 42 clickable bounding boxes (buttons, links, tabs, dropdowns) with accessible ARIA labels; these are promoted through T2b Kushalata-Visual to T3 Gyān as structured factoids. Vidya (Coder) then consults T3 Gyān and T2 Kushalata's existing Playwright test templates (carried over from the capstone's TypeScript API tasks) to generate a 42-test Playwright spec, with Parikshak (Tester) running the spec against a headless Chromium instance via Karmakarta's tool invoke gate and asserting that each `expect(locator).toBeVisible()` passes. Kriyākārī accepts on loop counter one after the first run reveals a flaky tab-click assertion that Parikshak catches and Vivchak promotes to a T2 Kushalata "always use `waitForLoadState('networkidle')` before tab clicks" skill template. This pipeline demonstrates that NoesisVision not only adds multimodal input handling but materially extends the class of software engineering tasks that Noesis can solve end-to-end: prior to adding Netralay, Noesis could test REST APIs with Zod schemas (SE50 Family 2) but could not generate end-to-end GUI tests because it had no way to observe the rendered DOM from a screenshot; after adding Netralay, the full GUI surface becomes accessible to the 14-agent roster with zero modifications to the twelve existing capstone agents or the six-tier promotion ladder semantics.

## 7.3 Product Roadmap P0 / P1 / P2: Four Product Lines with User Stories and MVP Scope

The Noesis kernel, 12-agent roster, and six-tier memory bus form a horizontal platform that can be instantiated into four vertically specialised products, organised into three priority tiers P0 (immediate, 0–6 months), P1 (medium-term, 6–18 months), and P2 (long-term, 18–36 months). The platform leverage principle is that each product reuses the identical C1/C2/C3 kernel code — the only differences are (i) which of the 12 Sanskrit agents are enabled in the spawn mask (some products do not require Anveshak's web search or Rakshak's SAST), (ii) the initial contents of T2 Kushalata skill templates loaded at boot, (iii) the immutable T6 Tattva YAML principles specific to the vertical, and (iv) the dashboard frontend skin. The four products are P0a NoesisSWE Box (laptop/edge SWE appliance), P0b NoesisResearch Scholar (academic writing agent), P1a NoesisCI (DevOps continuous-integration agent), and P1b Noesis Edu Tutor (undergraduate CS lab assistant), with P2 NoesisLegal / NoesisMed reserved as 24–36 month speculative plays requiring domain-specific regulatory certification before commercial deployment. For each product line, this section presents a single concrete user story with a named persona, an acceptance criterion that Kriyākārī must emit ACCEPT before the product declares success, and a narrowly scoped MVP feature set that reuses capstone artefacts wherever possible.

**P0a NoesisSWE Box — Edge-first AI software engineering appliance.** The NoesisSWE Box is a small-form-factor desktop appliance shipping with either a 96 GB RTX 4090 (high-end) or a 16 GB RTX 4070 Ti Super (mid-range), pre-loaded with Noesis, Ollama, the full six-tier memory bus, and the C2 capability kernel; the value proposition is "run a SWE-bench Verified–capable AI software engineer on your premises with zero API keys, zero data exfiltration risk, and one-click GitHub repo integration". *User Story.* Arjun, a 28-year-old senior backend engineer at a Series A SaaS startup handling personally identifiable health data of 120 000 Indian patients, is forbidden by company policy and by India's Digital Personal Data Protection Act (DPDPA) 2023 from uploading the company's private GitHub monorepo to any cloud LLM API. He receives a GitHub issue from the customer-support team: "the patient appointment booking form accepts a 13-digit Aadhaar number but the database schema defines the column as `aadhaar VARCHAR(12)`; fix the schema migration, add server-side Zod validation, write a regression test with 6 valid and 6 invalid fixtures, and update the Swagger/OpenAPI spec". Arjun connects the NoesisSWE Box to his desk's USB-C dock, clicks "Add Private Repo" on the dashboard, enters his locally-stored GitHub fine-grained personal access token (stored in T5 Yojana, encrypted with his YubiKey public key — never leaves the box), and pastes the GitHub issue body into the goal field. Kriyākārī must emit ACCEPT within 30 minutes, producing a pull-request diff that passes the company's 2 400 existing pytest cases, the new 12-fixture Zod validation test, and a Rakshak (Security) CVE scan that confirms the schema migration does not introduce SQL injection into the `aadhaar` query path. *MVP Scope.* The P0a NoesisSWE MVP reuses 95% of the capstone codebase verbatim: the 12-agent roster, the C1 T1→T6 promotion, the C2 spawn/invoke gates, the C3 deterministic audit manifest, and the Noesis-SE50 evaluation harness. The MVP adds only four adapter-layer modules that are outside the capstone scope: (i) a `GitHubIntegrationAdapter` that clones private repos via libgit2, writes the tree SHA and file contents to T1 Indriya, and opens a signed pull request with the Kriyākārī ACCEPT manifest in the PR body; (ii) a `PytestHarnessAdapter` that runs the company's existing test suite via Karmakarta's invoke gate and writes pass/fail factoids to T3 Gyān; (iii) a T6 Tattva `dpdpa-2023.yaml` principles file with the immutables "no PII may be written to T5 Yojana without AES-256-GCM encryption with a key held in HSE", "no outbound HTTP request may contain a column value tagged as PHI", and "Rakshak SAST must flag any raw f-string SQL construction"; (iv) a white-label skin of the Next.js 14 dashboard with the startup's logo and a "Compliance Audit" tab that exports a signed C3 manifest PDF for the DPDPA Data Protection Officer. The P0a MVP is scoped to 8 weeks of full-time work, with the Go/No-Go checkpoint being that the box can solve the ten TypeScript-API SE50 tasks against a private GitHub repo without making any outbound API calls other than to GitHub itself.

**P0b NoesisResearch Scholar — End-to-end academic writing agent.** The NoesisResearch Scholar product packages the Noesis kernel with T2 Kushalata skill templates specialised for academic writing: LaTeX section formatting, BibTeX citation management, IEEE/ACM conference proceedings style guides, arXiv abstract composition, and peer-review rebuttal letter drafting. *User Story.* Priya, a 22-year-old B.Tech final-year student at a NIT, has completed her capstone (a variant of Noesis itself) and has all the experimental data tables in CSV format, but she is blocked on writing the 22-page arXiv preprint and the 6-page CODS-COMAD 2027 submission because she struggles with academic prose structure and citation formatting. She opens NoesisResearch Scholar, drops her 15 CSV result files, her 4-page Marp viva deck PDF, and her three-page synopsis PDF into the dashboard, and types the goal: "produce a 22-page arXiv preprint in IEEEtran two-column format with the following 8 sections (abstract, introduction, related work, system architecture, methodology, implementation, evaluation, conclusion, 60+ references) from my data files; then produce a condensed 6-page CODS-COMAD 2027 submission extract; finally draft a 1-page cover letter to the PC chairs". Kriyākārī must emit ACCEPT within 4 hours, producing a .zip archive containing the arXiv .tex + .bib + figures, the CODS-COMAD .tex + .bib, and the cover letter, with the evaluation section's every numerical table exactly matching the CSV input files (verified by Parikshak's (Tester) deterministic checksum against the input CSV SHA-256 hashes), and with BibTeX entries verified by Anveshak (Researcher) against the Crossref OpenURL API so that no "gray literature" URL-only citations remain. *MVP Scope.* The P0b MVP reuses the capstone's full 12-agent roster with the only mask difference being that the Vidya (Coder) agent's role is remapped to "Writer", the Parikshak (Tester) agent's role is remapped to "FormatChecker", and the Karmakarta (Tooler) agent gains three new registered tools: `latex_compile`, `bibtex_check_crossref`, and `pdf_sha_extract_figures`. T2 Kushalata is pre-seeded with 48 skill templates drawn from the Overleaf IEEEtran documentation and the CODS-COMAD 2027 author instructions: e.g., "abstract must be 150–250 words, structured as 4 sentences (background, gap, method, results)", "related work section must be a 4-column comparative table for every conference paper over 6 pages", "every \citep command must resolve to a BibTeX entry with a DOI field". T6 Tattva is pre-loaded with a `scholar-ethics.yaml` principle file that mandates "Anveshak must never invent a citation not verifiable against Crossref", "Samanyakā must never paraphrase text longer than 3 consecutive words from a paper without adding a citation", and "Kriyākārī must reject any submission with a Turnitin-style similarity score above 15% computed by the `text_similarity` tool against a 10-million-paper Semantic Scholar dump". The MVP's novel component is the C3 determinism guarantee applied to academic writing: the same (goal, seed, input CSV) triple re-run produces bit-exact the same LaTeX file and the same BibTeX citation keys, which is an industry-first guarantee that allows Priya to regenerate her paper after fixing a single CSV row without worrying that the rest of the manuscript's prose or citations will drift nondeterministically. The P0b MVP is scoped to 6 weeks of full-time work.

**P1a NoesisCI — Autonomous DevOps and CI/CD remediation agent.** The P1-tier NoesisCI product is a drop-in replacement for human DevOps on-call rotations, integrating with GitHub Actions, GitLab CI, and Jenkins to autonomously triage failing CI pipelines, diagnose the root cause from build logs and stack traces, commit a fix, and push a follow-up commit that re-passes the pipeline; it targets mid-sized engineering teams of 20–100 engineers who spend 10–15% of their engineering capacity on CI toil. *User Story.* Rohit, a 31-year-old DevOps lead at a fintech unicorn with a 40-engineer backend team, is paged at 2:14 AM Indian Standard Time because the nightly Jenkins regression pipeline for the core payments service failed on step 47 of 128: "database migration V047__add_customer_fraud_score.sql deadlocked with concurrent writes, error code 1213 in AWS Aurora MySQL 8.0". Without NoesisCI, Rohit would log into the VPN, pull the 1 200-line build log, SSH into the Aurora read replica to examine the deadlock graph, and then either cherry-pick a hotfix to add `LOCK TABLES` explicitly or escalate to the database team for a 3-hour response window. With NoesisCI, the Jenkins webhook is pre-configured to POST every failing pipeline's build log, Git SHA, and job name to the NoesisCI FastAPI endpoint; the system autonomously spins up, runs Manan (Planner) → {Darshak (Analyst) on the deadlock log, Vidya (Coder) on the hotfix, Anveshak (Researcher) on MySQL 8.0 deadlock best practices, Parikshak (Tester) on the local migration test harness} → Samanyakā → Kriyākārī, commits the hotfix to a `noesisci/hotfix-deadlock-V047` branch, pushes it, and opens a GitHub PR with the signed C3 manifest attached. Kriyākārī must emit ACCEPT within 20 minutes of the webhook POST, the PR must pass the 2-minute smoke pipeline that Rohit's team has configured for hotfix branches, and the deadlock must not reproduce in the 100-iteration stress test that Parikshak (Tester) runs against a local Dockerised Aurora-compatible MySQL 8.0 instance via Karmakarta's invoke gate. *MVP Scope.* The P1a MVP reuses the capstone kernel, adds a `JenkinsAdapter` and `GitHubActionsAdapter` for webhook ingestion, extends Karmakarta with a `git_clone`, `git_commit`, and `git_push` tool suite, and pre-loads T2 Kushalata with 120 DevOps skill templates drawn from Stack Overflow's highest-voted CI/CD answers: "MySQL deadlock on ALTER TABLE → use `pt-online-schema-change` or `ALTER TABLE ... ALGORITHM=INPLACE, LOCK=NONE` in Aurora", "GitHub Actions npm install cache corruption → delete `~/.npm/_cacache` and re-run", "Docker buildx multi-platform QEMU segfault → pin `tonistiigi/binfmt:qemu-v7.0.0-28` image digest". T6 Tattva mandates that "NoesisCI must never force-push to a protected branch", "NoesisCI must never modify a file outside the `migrations/` or `.github/workflows/` directories if the failing step is a database migration", and "every Kriyākārī-accepted fix must be co-signed with an Ed25519 deploy key stored in HSE on the NoesisCI appliance". The P1a MVP is scoped to 12 weeks of full-time work, with a launch partner agreement already in principle with the capstone mentor's fintech firm.

**P1b Noesis Edu Tutor — Undergraduate CS lab assistant.** The P1-tier Noesis Edu Tutor is an on-premises lab assistant for Indian undergraduate B.Tech/B.Sc. ## 7.4 Long-Term Research: Formal Verification, Journal Submissions, and Intellectual Property

The final segment of the future-work roadmap addresses three long-term research tracks, each with a 24–48 month horizon and concrete success metrics: (i) mechanical formal verification of the C1 memory bus and C2 capability kernel correctness invariants in F* and Dafny, (ii) a two-stage journal submission pipeline to IEEE Transactions on Software Engineering (TSE) followed by Elsevier Journal of Systems and Software (JSS), and (iii) a provisional Indian patent disclosure for the C1 six-tier memory promotion capability-gate mechanism, specifically the combination of Vivechak-signed tier-adjacent-only promotion with the T6 Tattva immutable boot-time pinning. ### 7.4.1 Formal Verification: F* for the Memory Bus, Dafny for the Capability Kernel

The capstone establishes C1 and C2 correctness by construction via 100% unit-test branch coverage, exhaustive hypothesis property-based testing, and grep-level structural non-bypassability audits, but the invariants are not mechanically proved: a sufficiently creative refactoring could introduce a skip-tier promotion code path or a bypassable invoke-gate call site without the unit tests catching it. The long-term verification programme closes this gap by producing two independently machine-checked artefacts: a 6 000-line F* module that proves the C1 memory-bus invariants (tier adjacency, Vivechak-signature requirement, no back-door writes to tiers T2–T6) for a purely functional model of `MemoryBus.read`, `write_t1`, `promote`, and `demote`, and a 4 500-line Dafny module that proves the C2 capability-kernel invariants (three-term AND-mask for spawn, four-term AND-mask for invoke, HMAC signature check occurs before mask check, no call site in the kernel AST produces an OS side effect without transiting the invoke gate) for a model of `CapabilityToken`, `AgentRoster.spawn`, and `ToolRegistry.invoke`. The choice of two different provers is deliberate: F*'s dependent type system and refinement types are well-suited to the stateful, layered nature of the memory promotion ladder, while Dafny's imperative-while-program semantics and built-in SMT-backed lemma infrastructure are better suited to the bitmask-heavy integer arithmetic of the capability token masks.

The concrete F* verification targets for C1 are three lemmas, each corresponding to one clause of the C1 invariant stated in §1.7, plus an auxiliary non-interference lemma. **Lemma C1a (Write Entry Lemma).** `lemma write_t1_only_lowest_tier(bus: MemoryBus, cell: Cell) : Lemma (ensures write_t1(bus, cell).tier == T1)`. This lemma discharges the first C1 clause "no memory cell enters above T1 except via promotion" by showing that the only non-promotion write API `write_t1` always writes to exactly tier T1. **Lemma C1b (Promotion Adjacency Lemma).** `lemma promote_strictly_adjacent(bus: MemoryBus, cid: CellId, sig: VivechakSig) : Lemma (requires let m = lookup(bus, cid) in Some? m /\ Some?.v m < T6) (ensures let m' = promote(bus, cid, sig) in tier(Some?.v m') = tier(Some?.v m) + 1)`. This discharges the "strictly tier-adjacent" clause by showing that a successful `promote` call increases the tier by exactly one, never more; the proof proceeds by case analysis on the 5 possible source tiers T1–T5 and uses F*'s `SMTPat` pattern hints to discharge the bit-shifting arithmetic in the `TIER_BIT` macro. **Lemma C1c (Signature Requirement Lemma).** `lemma promote_requires_vivechak_sig(bus: MemoryBus, cid: CellId, sig: VivechakSig, bad_sig: VivechakSig) : Lemma (requires sig != bad_sig) (ensures promote(bus, cid, bad_sig) raises VivechakSignatureInvalid)`. This discharges the "Vivechak must co-sign" clause by showing that any mismatched signature causes the promote function to abort; the proof uses F*'s `exact` tactic with a pre-computed Ed25519 signature oracle. The auxiliary **Lemma C1d (Non-Interference of T6 Tattva).** `lemma t6_immutable_after_boot(bus1: MemoryBus, bus2: MemoryBus, step: BusStep) : Lemma (requires t6_cells_equal(bus1, bus2)) (ensures t6_cells_equal(bus1, step(bus2)))` shows that no kernel step (read, write_t1, promote, demote) can ever mutate a T6 Tattva cell once the boot procedure has pinned the initial T6 contents; this is the formalisation of Maxim 6 *Nirikṣaṇaṃ nityam* as a machine-checked non-interference property.

The Dafny verification targets for C2 are similarly three lemmas plus an auxiliary non-bypassability theorem, all stated over a simple imperative model of the kernel with 64-bit integer bitmasks. **Lemma C2a (Spawn AND-Mask Lemma).** `lemma SpawnMaskConjunction(parent: CapabilityToken, child: Role) requires ValidToken(parent) ensures SpawnAllowed(parent, child) ==> (RolesMatch(parent, child) && TiersSubset(parent, child) && HasOpSpawn(parent))`. This lemma is proved by unfolding the definition of `SpawnAllowed` into the three-term AND and then applying Dafny's built-in `bitwise` arithmetic tactic to show that the conjunction does not short-circuit. **Lemma C2b (Invoke AND-Mask Lemma).** `lemma InvokeMaskFourTerms(caller: CapabilityToken, tool: RegisteredTool) requires ValidToken(caller) ensures InvokeAllowed(caller, tool) ==> (RolesMatch(caller, tool) && TiersSubset(caller, tool) && HasOpInvoke(caller) && ToolCapSubset(caller, tool))`. This is the four-term invoke-gate variant of C2a. **Lemma C2c (Signature First Lemma).** `lemma SignatureCheckedBeforeMask(token: CapabilityToken) ensures exists trace: list<KernelEvent> :: ValidTrace(token, trace) ==> (SigCheck in trace) before (MaskCheck in trace)`. This lemma formalises the crucial security property that a tampered token (e.g., an attacker flipping the OP_MINT bit via LLM prompt injection) fails the HMAC signature check before the kernel ever evaluates the mask bits, so the attacker cannot learn anything about the mask layout from timing side channels. The auxiliary **Theorem C2d (Structural Non-Bypassability).** `theorem NoSideEffectWithoutInvoke(ast: KernelAST, node: ASTNode) requires WellFormedAST(ast) ensures ProducesOSEffect(node) ==> TransitiveCall(node, ToolRegistry.invoke)`. This theorem is proved by structural induction over the kernel AST, exploiting the fact that the Dafny model imports the actual Python kernel's AST via a `fromPython` compile-time macro — it therefore applies not to a toy model but to the precise call graph of the shipped `noesis.kernel.capability` module, giving end-to-end machine-checked non-bypassability.
