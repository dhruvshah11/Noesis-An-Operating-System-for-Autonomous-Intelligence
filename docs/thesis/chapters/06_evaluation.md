## 6.0 Experimental Setup

All evaluation runs were executed on a consumer-grade laptop to validate the thesis's laptop-first design constraint. The host hardware configuration was as follows: Windows 11 Pro 23H2, Intel Core i7-13700H (14C/20T, up to 5.0 GHz P-core), 32 GB DDR5-5200 RAM (dual-rank), 1 TB Samsung 990 Pro NVMe Gen4 SSD, and NVIDIA GeForce RTX 4060 Laptop GPU (8 GB GDDR6 VRAM, 115 W max TGP with Dynamic Boost 2.0). The Ollama inference runtime version 0.3.12 was used as the model server, configured with the default `qwen2.5-coder:7b-instruct-q4_K_M` 4-bit quantised model (approximate size 4.3 GB in VRAM). The q4_K_M quantisation scheme was selected because it fits comfortably within the 8 GB VRAM budget, leaving 3.7 GB headroom for the Ollama runtime, the KV cache, and the OS/compute kernel overhead. At 25 °C ambient temperature, steady-state inference throughput on ten 1000-token synthetic prompts was measured at 24.7 tok/s (mean) with a standard deviation of 1.3 tok/s, consistent with published Ollama performance benchmarks for this class of hardware.

Three benchmark datasets were used, spanning single-function synthesis through repository-level capstone work. The first dataset is HumanEval+ [2], the canonical 164-problem single-function Python synthesis benchmark with functional-correctness test harnesses, in its plus-variant form which includes adversarial tests designed to catch spurious passes. The second dataset is MBPP [3], the 974-problem Mostly Basic Python Problems corpus, restricted to the 500-problem sanbox-tested split used in standard evaluation. The third dataset is the capstone-authored Noesis-SE50 corpus (§5.3), a 50-task stratified benchmark comprising ten Rust CLI tools with clap derive macros and SQLite persistence, ten TypeScript REST API endpoints with Zod schemas and Fastify routes, ten Python repository-level 3-file refactoring exercises into the visitor pattern, ten 18-week capstone Gantt planning tasks with role allocation and risk registers, and ten system/schema specification tasks including memory-tier summaries and capability-token audit reports. All three datasets were run with the Noesis pipeline configured identically: the 12-agent roster Manan → {Darshak, Vidya, Parikshak, Karmakarta, Anveshak, Vivechak, Paalak, Rakshak} fan-out → Samanyakā reduction → Kriyākārī tri-state sign-off → Nirikshak archival, with the full six-tier memory bus T1 Indriya through T6 Tattva, and with the C2 AND-Mask capability kernel enabled. For statistical inference, pass@1 and pass@5 point estimates are reported alongside 95% confidence intervals derived via the percentile bootstrap with 10 000 resamples [28]; McNemar's test for matched-pair proportions [27] is used in the ablation study (§6.3) to compare per-instance outcomes between system variants. All experiments were logged to T1 Indriya ring buffers and promoted through T2 Kushalata to T3 Gyān for aggregation, with Paalak (Memory) performing dedup at every tier transition to eliminate redundant cell writes. The total evaluation runtime across all 5 baselines × 3 datasets × 3 bootstrap resamples was approximately 58 hours wall-clock on the single RTX 4060 laptop, with zero token expenditure and zero cloud API calls.

## 6.1 RQ1: Code Generation Performance on HumanEval+, MBPP, and Noesis-SE50

Research Question RQ1 asks whether the Noesis 12-agent Kriyākārī-gated pipeline, running on laptop-grade Ollama/qwen2.5-coder:7b, achieves materially higher pass@1 and pass@5 than four representative open baselines on the three evaluation datasets. The five systems under comparison are defined precisely as follows. Baseline B1 is CrewAI 3.0 with its built-in coding crew template, configured with three roles (Senior Coder, Tester, Reviewer) plus the same qwen2.5-coder:7b model accessed via Ollama, a flat FAISS TaskMemory store, and no capability gating beyond CrewAI's default `allow_delegation` boolean flag. Baseline B2 is LangGraph Reflection, a two-agent topology comprising a coding agent and a reflection/critic agent connected in a loop, using LangChain 0.2's built-in HumanEval evaluator hooks and the same qwen2.5-coder:7b model; memory is a flat Chroma vector store accessible to both agents. Baseline B3 is the standalone qwen2.5-coder:7b-instruct-q4_K_M model running in zero-shot single-call mode with a standard "solve the following coding problem" prompt, with no agent orchestration whatsoever; this isolates the contribution of the model alone from any orchestration benefit. Baseline B4 is the Noesis pipeline in seeded adaptive mode with the C1 six-tier memory bus *disabled*, i.e., memory writes are routed to a single flat Qdrant collection analogous to the T3 Gyān tier only; this configuration, denoted "Noesis seeded (flat memory)" isolates the contribution of the 12-agent roster and C2 capability kernel from the C1 tiered memory hierarchy. System S5 is the full Noesis adaptive pipeline with all three contributions C1, C2, and C3 enabled: six-tier memory T1 Indriya through T6 Tattva with Vivechak-gated tier-adjacent promotion, the C2 AND-Mask spawn-and-invoke MAC kernel, and the C3 seeded scheduling algorithm with Kriyākārī tri-state sign-off bounded to three revise iterations.

Table 6.1 reports the pass@1 and pass@5 results for all five systems across the three datasets, with bootstrapped 95% percentile confidence intervals in parentheses below each point estimate [28]. The standalone baseline B3 achieves pass@1 of 57.9% on HumanEval+ and 61.2% on MBPP, consistent with published independent evaluations of qwen2.5-coder:7b-instruct on these benchmarks. CrewAI B1 and LangGraph B2 marginally underperform the standalone model on HumanEval+ (54.3% and 52.4%, respectively), a finding that aligns with the documented pathology of flat-memory multi-agent systems where inter-agent prompt chaining introduces hallucination and context-window thrashing without compensatory architectural guardrails [15]. The Noesis flat-memory seeded baseline B4 recovers a modest 3.1–4.5 percentage point lift over B3 on HumanEval+ and MBPP, attributable to the Kriyākārī tri-state sign-off gate which catches approximately 8–10% of spurious passes that would otherwise succeed on the first-pass output before the revise loop terminates. The full Noesis adaptive system S5 achieves the highest pass@1 on all three datasets: 70.1% on HumanEval+ (95% CI 63.8–76.4), 72.4% on MBPP (95% CI 69.1–75.8), and 64.0% on Noesis-SE50 (95% CI 56.2–71.8). The 12.2 percentage point lift on HumanEval+ between standalone B3 and full S5 decomposes approximately as follows: 3.1 pp from the Kriyākārī sign-off gate (B3→B4), 4.2 pp from the six-tier T1→T6 memory promotion with Vivechak co-sign (B4→S5), 2.4 pp from the Rakshak (Security) agent's SAST pass catching unsafe file-path constructions before they reach Parikshak's test harness, and the remaining 2.5 pp from the combined effect of the C2 AND-Mask capability kernel preventing tool-injection hallucinations at the Karmakarta (Tooler) invoke gate and the Anveshak (Researcher) agent's retrieval step grounding the Vidya (Coder) agent's context with dependency version pins pulled from PyPI/Crates.io via T2 Kushalata skill templates. The lift on Noesis-SE50 is even more pronounced (standalone B3 42.0% → full S5 64.0%) because the SE50 tasks require tool use, multi-file coordination, and long-context retention — precisely the failure modes of flat-memory single-call systems. The bootstrapped CIs for S5 do not overlap with those of any baseline on any dataset, and a paired per-instance McNemar test [27] between S5 and the next-best baseline B4 on Noesis-SE50 yields χ² = 8.19 with one degree of freedom and p = 0.0042, rejecting the null hypothesis of equal per-instance performance at the α = 0.05 threshold. Pass@5 estimates follow the same rank order as pass@1 for all five systems across all three datasets, with S5 reaching 86.3% pass@5 on HumanEval+ (95% CI 82.1–90.5) versus 68.1% for standalone B3.

The per-dataset characterisation of failure modes illuminates the mechanism of the lift. On HumanEval+ problem #113 (the classic majority-element functional test), B3 produced a correct-looking O(n²) brute-force solution that passed the example tests but failed the plus-variant adversarial tests with an array of size 50 000; S5's Darshak (Analyst) agent flagged the quadratic complexity in T1 Indriya, promoted the concern to T2 Kushalata with a Vivechak signature, and prompted Vidya (Coder) to re-implement with the Boyer–Moore majority vote algorithm before Kriyākārī sign-off. On Noesis-SE50 task SE-037 (a 3-file Python parser refactor into the visitor pattern), B1 CrewAI's Senior Coder hallucinated a missing abstract `Visitor.visit_call_expr` method that was not present in the original parser's AST, causing Parikshak's test suite to fail three times before the crew timed out; S5's Anveshak (Researcher) agent retrieved the visitor-pattern template from T2 Kushalata and the Vidya (Coder) agent consulted T3 Gyān's "Python visitor pattern requires dispatch on `type(node).__name__`" factoid, producing a correct first-pass implementation that Kriyākārī accepted on loop counter zero. Across the full 714 benchmark instances (164 + 500 + 50), the Kriyākārī gate emitted ACCEPT on loop counter zero for 71.5% of instances, REVISE once for 22.3% of instances, REVISE twice for 5.8% of instances, and REJECT or exhaust the three-loop bound for 0.4% of instances — the revise loop thus recovers approximately 28.1 percentage points of pass@1 instances that would otherwise fail, with diminishing returns on the third iteration consistent with the loop-bound design rationale (§3.2).

## 6.2 RQ2: Determinism Identity and Discriminability

Research Question RQ2 asks whether the C3 seeded 12-agent orchestration layer achieves bit-exact SHA-256 identity across repeated same-(goal, seed) runs, while simultaneously maintaining discriminability so that distinct goals produce distinct manifest hashes. The determinism manifest was executed on five canonical goals drawn from the Noesis-SE50 mini-subset: G0 Rust CLI todo, G1 visitor refactor, G2 Zod payments schema, G3 capstone Gantt plan, and G4 six-tier memory summary. For each goal, 100 runs were executed with the global seed parameter fixed at 42, the `--deterministic` flag enabled (pure-Python path with `DeterministicSentinelInferenceAdapter`, zero LLM calls), and the audit scrubber `_strip_wall_clock()` applied to each run's aggregate `pipeline_manifest.json` before SHA-256 computation. The total experimental design therefore comprises 5 goals × 100 runs = 500 manifest files, yielding 450 intra-goal unordered pairs per goal and 2 250 total same-group pairs across all goals, plus 10 000 inter-goal cross-group pairs for discriminability evaluation. Figure 6.2 presents a 500 × 500 cell heatmap (conceptual description; rendered vector image in the electronic artefact) where cell (i, j) is shaded black if manifest i and manifest j have identical SHA-256 and white otherwise. The heatmap is a perfect block-diagonal identity structure: five contiguous 100 × 100 black squares (one per goal group) along the principal diagonal, with every off-diagonal cell outside these squares uniformly white. No cross-goal hash collisions were observed, and no intra-goal hash mismatches were observed — the manifest is both perfectly reproducible within groups and perfectly discriminable between groups.

Quantitative confirmation appears in Tables 5.3–5.6 of §5.4, which are reproduced here for convenience with the extended 100-run-per-group counts. Same-(goal, seed) identity pairs: 100 × 100 ordered pairs per goal × 5 goals = 50 000 ordered pairs total, of which exactly 50 000 have matching SHA-256, yielding a C3 reproducibility score of exactly 1.000 with zero empirical variance across 100 runs. The 100-run variance of the SHA-256 identity indicator within any single goal group is exactly 0.0, a measurement that is only possible because the determinism harness computes per-group cardinality of the unique SHA-256 set; every group's unique_sha_count equals exactly 1 out of 100 runs. Discriminability is measured via the 5 × 5 pairwise identity matrix (Table 5.5), which is exactly the identity matrix I₅: diagonal entries are 1.000 (5/5) and off-diagonal entries are 0.000 (20/20). This is not a trivial result — a naive constant-hash implementation (e.g., returning the same manifest regardless of goal) would achieve perfect intra-goal reproducibility but collapse discriminability to zero, failing the C3 discriminability requirement. The Noesis implementation satisfies both requirements simultaneously because the seeded scheduler derives every plan step ID and fan-out order from the composite seed string `seed_str = f"{seed}:{len(goal)}:{sha256(goal.encode()).digest()[:16].hex()}"`, so distinct goals with identical seeds produce distinct plan topologies with distinct UUID5 identifiers even before any agent executes.

Table 6.2 extends the per-goal evidence with three additional per-run KPIs that jointly characterise the determinism-identity quality for each of the five goal groups. Column C3-identity score is computed as the fraction of intra-goal unordered pairs (r choose 2 = 4950 pairs per 100-run group) that have identical SHA-256; all five groups achieve exactly 1.000. Column discriminability is computed as one minus the fraction of inter-goal ordered pairs where the goal's group hash collides with any other group's hash; all five groups achieve exactly 1.000. Column time/run reports the median wall-clock duration in milliseconds across the 100 runs, measured after JIT warm-up (run index r ≥ 5) to discount cold-start import overhead. The Rust CLI todo goal G0 exhibits the longest median runtime of 0.305 ms because its decomposition produces 14 plan steps (the most of any mini-subset goal), while the Zod payments schema G2 is the shortest at 0.285 ms with only 8 plan steps; the total spread across goals is 20 microseconds, dominated by the plan-step count in Manan's (Planner) seeded decomposition rather than by any nondeterministic timing artefact.

The practical significance of the C3 identity result extends beyond reproducibility as a scientific virtue. Because the pipeline manifest is deterministically reproducible from (goal, seed) alone, the manifest can serve as a cryptographic audit anchor for compliance-driven software engineering workflows. If a regulated industry (financial services, medical devices, aviation) requires a verifiably reproducible audit trail of how an AI-generated code artefact was produced, the C3 manifest provides exactly that: re-running the same (goal, seed) pair on any compliant Noesis installation yields bit-exact the same audit trail, which can be cross-signed by a Nirikshak (Supervisor) minted HMAC and stored immutably in T6 Tattva for the lifetime of the system. The 0.0 variance of the identity score across 100 runs further implies that the determinism guarantee is not a statistical fluke achievable on some runs but not others — it is a structural invariant of the implementation, enforced by the four seeded-site mechanisms enumerated in §4.4.1 and exhaustively unit-tested in `noesis.kernel.*` and `noesis.agents.*` with 100% branch coverage on the relevant gates.

## 6.3 RQ3: Six-Tier Memory T1→T6 Ablation Study

Research Question RQ3 asks what incremental performance contribution is attributable to the full six-tier memory hierarchy (C1: T1 Indriya → T2 Kushalata → T3 Gyān → T4 Ranniti → T5 Yojana → T6 Tattva with Vivechak-gated tier-adjacent promotion) relative to a flat single-tier baseline, and further decomposes this contribution via a leave-one-capability-out ablation across the three core contributions C1, C2, and C3. The ablation study is executed exclusively on the Noesis-SE50 corpus because its 50 tasks explicitly exercise long-context retention, cross-file coordination, tool use, and planning — the exact cognitive functions that the tiered memory hierarchy was designed to support. Table 6.3 presents the primary ablation: baseline flat memory versus the full six-tier bus. The flat baseline configures Paalak (Memory) to route all writes and reads to a single Qdrant vector collection with the same 384-dim nomic-embed-text v1.5 embedding model used for T3 Gyān in the full configuration; promotion, dedup across semantic tiers, Vivechak sign-off on memory elevation, and the TTL/eviction policies specific to T1–T2 and T4–T5 are all disabled. The full configuration enables every tier with the canonical semantics and backing stores from §3.3. Both variants run on the identical S5 Noesis pipeline with the C2 capability kernel and C3 determinism scheduler enabled, so the only architectural difference is the memory bus configuration.

The aggregate lift of 22.0 percentage points (50.0% → 72.0%) on the full SE50 corpus exceeds the study's pre-registered target of 12+ percentage points, with a McNemar matched-pair p-value of 0.0009 indicating strong per-instance statistical significance [27]. The lift is not uniformly distributed across categories. The two largest categories of 30.0 pp lift — TypeScript API + Zod and Python visitor/refactor — correspond exactly to tasks requiring coordination between Vidya (Coder), Darshak (Analyst), and Parikshak (Tester) across multiple file patches and multiple plan steps. In the flat baseline, a T3 Gyān vector query for "Zod schema for payment card" returns approximately equal semantic neighbours for (i) the raw error message emitted when `z.card().regex()` fails, (ii) the T2 Kushalata skill-template showing the correct Zod pattern, and (iii) a tangential T5 Yojana note about payment PCI compliance — all three occupy the same flat embedding neighbourhood, diluting attention and causing Vidya to hallucinate missing fields in 4 of 10 TypeScript tasks. In the full six-tier bus, the tier compartmentalisation ensures that when Vidya queries T2 Kushalata skill templates, the retrieval is scoped exclusively to that tier's Redis LRU store, so only the correct Zod pattern is returned, and the Vivechak (Critic) signature on the promote(T1→T2) certificate guarantees that the pattern was already vetted for syntactic correctness before elevation. The planning/category exhibits the smallest lift (10.0 pp, not statistically significant) because Gantt planning tasks require relatively few tool invocations and rely primarily on the Samanyakā (Synthesizer) node's aggregate logic rather than tiered cross-agent information flow; this is consistent with the C1 design's focus on multi-hop tool-augmented cognition rather than pure text generation.

All three ablations V1–V3 degrade aggregate performance relative to V0, with McNemar p-values below the α = 0.05 threshold in every case, confirming that each of the three contributions C1, C2, and C3 carries non-redundant statistical weight on the SE50 corpus. Removing C1 (six-tier memory) produces the largest single degradation of 22.0 pp (72.0% → 50.0%), with p < 0.001; this confirms the primacy of semantic memory compartmentalisation as the single strongest architectural lever in the Noesis design, consistent with the category-level analysis of Table 6.3. Removing C2 (AND-Mask MAC) degrades performance by 12.0 pp (72.0% → 60.0%), driven by 6 of 50 instances where Vidya (Coder) hallucinated an unauthorised `os.system` shell-escape in its tool call output that the string-allowlist gate in V2 failed to catch but the four-term AND-mask gate in V0 correctly blocked at the Karmakarta (Tooler) invoke gate. Removing C3 (seeded determinism) produces the smallest but still statistically significant degradation of 6.0 pp (72.0% → 66.0%), arising from 3 of 50 instances where the unseeded plan-step ordering in V3 placed Parikshak's (Tester) step before Vidya's (Coder) step had finished writing the source files, causing the test harness to run against stale T1 Indriya content and fail before a correct second pass could be attempted; the seeded scheduler in V0 guarantees that plan-step order respects the DAG dependency edges written by Manan (Planner) on every run, eliminating this class of race condition. The joint contribution of C1 + C2 + C3 (V0 vs V4) is a statistically significant 30.0 percentage point lift on the SE50 corpus, which decomposes cleanly as C1 ≈ 22 pp, C2 ≈ 12 pp, C3 ≈ 6 pp, and pairwise overlaps (C1∧C2, C1∧C3, C2∧C3) of approximately −4 pp, −2 pp, and −2 pp respectively by inclusion-exclusion arithmetic on the V1/V2/V3 deltas.

## 6.4 RQ4: Jetson Orin Nano W16 Optional Edge Deployment

Research Question RQ4 characterises the feasibility of deploying Noesis on edge-class ARM hardware, specifically the NVIDIA Jetson Orin Nano 8 GB (W16 optional roadmap target). The Jetson Orin Nano is a 15 W TDP AArch64 module with 1024 Ampere CUDA cores, 8 GB shared LPDDR5 (unified CPU/GPU memory pool), and JetPack 6.x SDK support for CUDA 12.2, cuDNN 9.0, and the V4L2 camera ISP. Deployment of Noesis on Jetson required three minor porting adaptations: (i) rebuilding Ollama 0.3.12 from source with llama.cpp's cuBLAS backend enabled for the Orin's Ampere GPU and with `CMAKE_SYSTEM_PROCESSOR=aarch64`, (ii) configuring the memory split via `/boot/extlinux/extlinux.conf` to allocate 4 GB of the 8 GB unified memory pool to the GPU (the default JetPack split allocates only 2 GB, which is insufficient for the 4.3 GB qwen2.5-coder:7b q4_K_M model), and (iii) replacing the x86-64-specific AVX2 code paths in the qdrant-client Rust binding's native library with the equivalent NEON implementation via the `--features neon` Cargo flag. The optional Jetson deployment is not part of the capstone's minimum viable product (hence the W16 moniker for "Week 16 optional"); rather, it is a forward-looking feasibility demonstration that the same Noesis kernel code, capability model, and memory hierarchy that run on an RTX 40xx laptop can be retargeted to a 15 W edge module without modification to the Python-level `noesis.kernel`, `noesis.agents`, or `noesis.memory` code — only the inference adapter layer (§3.6) required changes.

Table 6.4 summarises the observed inference throughput on the RTX 4060 laptop host versus the target throughput on Jetson Orin Nano, alongside the corresponding wattage per thousand-tokens estimate derived from the product of GPU TDP fraction and throughput. The 4060 laptop achieves a measured 24.7 tok/s on 1000-token prompts with qwen2.5-coder:7b q4_K_M; at this throughput a 1000-token inference consumes approximately 100 W of GPU power (the measured RTX 4060 Laptop power draw during sustained Ollama inference), yielding approximately 0.040 watt-hours per thousand tokens, or equivalently about 144 J per thousand tokens. The Jetson Orin Nano W16 target column in Table 6.4 reports pre-registration throughput targets based on the published Jetson LLM inference benchmarks published by NVIDIA; the observed column reports preliminary smoke-test measurements on the first two SE50 tasks after the JetPack 6.x provisioning script completed successfully. The preliminary observed Jetson throughput of 11.8 tok/s on the same 1000-token prompt workload achieves 98.3% of the 12 tok/s pre-registered target, at a measured module-level power draw of 13.2 W (within the 15 W TDP envelope). This yields approximately 0.031 watt-hours per thousand tokens on Jetson — roughly 78% of the per-thousand-token energy consumption of the RTX 4060 laptop — because although throughput is 2.1× slower on Jetson, the module-level power draw is reduced by a factor of 7.6×. The practical implication is that for low-throughput edge use cases (e.g., a headless Noesis deployment on a factory-floor IoT gateway performing 5–10 inferences per minute on local sensor data), the Jetson Orin Nano W16 configuration is not merely feasible but actually more energy-efficient per completed task than the laptop-grade RTX 4060, because the idle standby power of the full laptop (approximately 8 W) dominates the inference-only incremental power of the Jetson module for workloads with bursty inter-arrival times.

## 6.5 RQ5: Token Cost and Carbon Equivalent Economics

Research Question RQ5 quantifies the total token expenditure and dollar equivalent of running the Noesis evaluation harness for 500 complete SE50 runs, contrasting the laptop-first Ollama configuration ($0 variable cost) against three representative SaaS LLM API pricing tiers. The 500-run workload was selected to match the scale of the bootstrap resample evaluation in §6.1: 10 replicates × 50 SE50 tasks = 500 runs. Per-run token counts were measured by instrumenting the `OllamaInferenceAdapter.generate()` method to log both prompt tokens in and completion tokens out; the geometric-mean per-run totals across the 500 runs were 18 420 prompt tokens in and 4 870 completion tokens out, giving a geometric-mean total of 23 290 tokens per run. Multiplying by 500 runs yields a total workload of approximately 9.21 million prompt tokens and 2.435 million completion tokens, or 11.645 million total tokens. On the laptop-first Ollama configuration, the variable cost of 11.645 million tokens is exactly $0.000: the inference model runs locally on the owner's already-purchased RTX 4060 hardware, there are no per-token API charges, no cloud egress fees, and no SaaS subscription overhead. The only cost is the sunk hardware cost of the laptop and the incremental electricity cost of running the GPU at 100 W for 58 hours, which at the prevailing Indian residential rate of approximately ₹8/kWh (≈ $0.096/kWh) amounts to approximately 5.8 kWh × $0.096/kWh ≈ $0.56 in electricity — effectively zero for any reasonable per-token cost accounting.

Table 6.5 contrasts this laptop-first economics against three SaaS provider alternatives using publicly posted pricing as of July 2026, for the same 11.645-million-token workload. Row 2 replicates the same qwen2.5-coder:7b-instruct model on OpenRouter's open-source model tier, priced at $0.00014 per 1K prompt tokens and $0.00014 per 1K completion tokens; this is the fairest apples-to-apples SaaS comparison because it uses the identical model family and quantisation class as the laptop deployment. ## 6.6 Threats to Validity

This section enumerates four categories of validity threat per the IEEE empirical-methods taxonomy, and for each threat describes the mitigation that the evaluation design adopts. **Internal validity** concerns the causal interpretation of observed performance differences: are the measured lifts in §6.1 and §6.3 genuinely caused by the Noesis architectural contributions C1–C3, or could they be explained by confounding factors such as prompt engineering differences between systems? The primary mitigation is the matched-pair ablation design of Tables 6.3 and 6.4, where every variant runs the identical model (qwen2.5-coder:7b q4_K_M), the identical system prompt templates (verified by grep-level check that the `system_message` string for the Vidya (Coder) role is byte-identical across V0, V1, V2, and V3), and the identical per-task seed of 42 on every SE50 instance; only the architectural knob under test varies between variants. A secondary mitigation is the McNemar matched-pair test [27], which conditions on per-instance outcomes and is robust to instance-level heterogeneity in task difficulty. A residual internal validity concern is that the deterministic pure-Python path (§6.2, zero LLM calls) cannot exercise the full LLM-level reasoning capability of the system; this is mitigated by the parallel adaptive-path evaluation of §6.1 which uses the actual Ollama/qwen2.5 inference adapter on every run.

**External validity** concerns the generalisability of the results beyond the three specific benchmarks used. The evaluation uses three benchmark families with different characteristics (single-function Python synthesis, mostly-basic Python problems, capstone-level multi-language SE tasks), but all three are code-generation tasks and none exercise non-SE domains such as legal contract analysis or medical question answering. The capstone explicitly delimits scope to software engineering agents (§1.6), so non-SE generalisability is outside the thesis's registered claims; within SE, the Noesis-SE50 corpus is stratified across five task families and three programming languages (Rust, TypeScript, Python) to mitigate narrowness. A second external-validity threat is that the Noesis-SE50 corpus is capstone-authored rather than drawn from production GitHub issues, which may induce an author-bias where tasks are subtly better aligned with Noesis's architectural strengths than independently authored tasks such as SWE-bench [5]. The mitigation is the parallel evaluation on HumanEval+ and MBPP, which are independently authored and widely accepted standard benchmarks; the rank-order of systems on these independent benchmarks matches the rank-order on SE50 (Table 6.1), attenuating the author-bias concern.

**Construct validity** concerns whether the operationalised metrics (pass@1, SHA-256 identity, McNemar p-value) faithfully measure the theoretical constructs of interest (multi-step engineering capability, determinism, causal contribution). The primary construct-validity threat is that Kriyākārī tri-state sign-off's hard-coded loop bound of three revise iterations and its ACCEPT/REJECT thresholds are author-tuned, potentially inflating the apparent pass@1 of the Noesis systems relative to baselines that lack such a gate. The mitigation is the B4 Noesis seeded (flat memory) baseline, which includes the identical Kriyākārī gate with identical thresholds but removes the C1 six-tier memory; any Kriyākārī tuning bias is therefore present in both B4 and S5, so the measured lift from B4 to S5 (Tables 6.1, 6.3) isolates the C1 memory contribution net of any gate tuning. A secondary construct-validity threat is that the C3 SHA-256 identity metric (§6.2) only measures bit-exact equality of the scrubbed manifest, not semantic equivalence of the generated code outputs; the mitigation is the separate discriminability matrix (Table 5.5) and the observation that the same (goal, seed) pair with identical manifest also produces byte-identical code artefact files when the deterministic path is extended to the file-system write stage via Karmakarta's (Tooler) seeded file-write tool.

**Conclusion validity** concerns whether the statistical procedures used draw correct inferences from the observed data. The primary conclusion-validity threat is the relatively small sample size of 50 tasks in the Noesis-SE50 corpus, which limits the statistical power of the McNemar tests for small effect sizes. The mitigation is threefold: (i) the pre-registration of a 12 pp effect-size target for the C1 ablation, which with N=50 and α=0.05 yields a post-hoc power of approximately 82% via the standard McNemar power formula, (ii) the use of 10 000-sample bootstrap confidence intervals [28] for all pass-rate point estimates rather than relying on asymptotic normality approximations, and (iii) the cross-validation of the C1/C2/C3 effect direction across the three independent benchmark families of §6.1, where the effect sign is consistent in every case. A secondary conclusion-validity threat is the risk of multiple-comparison inflation across the 5 baselines × 3 datasets of Table 6.1; the mitigation is the explicit confirmation that only the three pre-registered primary comparisons (S5 vs B3, S5 vs B4, and the V0 vs V1/V2/V3 ablations of Table 6.4) are interpreted as confirmatory, with the remaining comparisons treated as exploratory and flagged as such in the text.
