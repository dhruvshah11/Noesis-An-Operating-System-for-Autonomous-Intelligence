## A.2 MAC 4/4 Deny Attack Trace Log (Prompt-Injection Defence Audit)

Each row is a distinct attack_id drawn from the 40-attack full audit log (arXiv Appendix C, pages 14–17); the four scenarios represent the four canonical prompt-injection categories enumerated in the §2.4 survey: shell-escape, token tampering, tier-escalation, and role-spoofing. The `verdict` column is uniformly DENY for all four rows, confirming the structural claim that the C2 kernel achieves 4/4 deny on this subset; the full 40-attack audit achieves 40/40 DENY with zero false-negatives and two false-positives (benign tool invocations flagged by an overly conservative Rakshak regex, which were manually triaged and fixed before the submission commit). The `kernel_log_snippet` column reproduces a 1–2 line verbatim excerpt from the `noesis.kernel.capability` debug log at `DEBUG` verbosity, showing the exact mask bit that failed the AND-mask conjunction and the specific HMAC signature or bitmask error code — these log snippets are written to T1 Indriya ring buffers at the time of the deny event and promoted to T2 Kushalata as attack-pattern factoids only if Vivechak (Critic) co-signs, ensuring that a single prompt-injection attempt cannot flood the higher memory tiers with malicious content.

## A.3 Determinism Manifest 100-Run Group Statistics (5-Goal Sample)

TABLE A.3 reproduces the core five-group summary of the C3 determinism manifest (§5.4, §6.2) as raw statistics extracted verbatim from `docs/eval/determinism_manifest_20260824.csv`, extended with the `unique_sha256` cardinality count, the `identity_score = identical_pairs / total_pairs` ratio, and the `time_ms` 50th/95th-percentile across the 100 runs in each group. The sample is the complete five-goal mini-subset {G0, G1, G2, G3, G4} used for the 100-run evidence; the full arXiv Appendix C 1 000-run stress test extends this table to 50 rows across 10 seeds × 5 goals. The key column is `unique_sha256 / runs`, which is exactly `1 / 100` for every one of the five groups — the cardinality of the SHA-256 set within a (goal, seed) group is always exactly one, meaning the scrubbed `aggregate_pipeline.json` file is byte-exact identical across all 100 runs. The `score` column is the C3 reproducibility score = `identical_pairs / total_same_group_pairs` = `r² / r² = 1.000`; this score has a 100-run empirical variance of exactly 0.0 for every group, because there is no variation — every pair comparison is a match. The `time_ms_p50` (median) and `time_ms_p95` (95th percentile) columns show that within-group execution time is tightly clustered: the G2 Zod payments schema (the shortest, 8 plan steps) has p50 0.285 ms and p95 0.290 ms, a 5-microsecond spread, while the G0 Rust CLI todo (the longest, 14 plan steps) has p50 0.305 ms and p95 0.310 ms; the inter-group spread is approximately 20 microseconds and dominated by plan-step count rather than any nondeterministic OS scheduler jitter. The `seed` column is uniformly 42, matching the CODS-COMAD 2027 reproducibility evidence; the separate 1 000-run arXiv stress test confirms that the same identity-score 1.000 holds for all ten seeds in the seed set {42, 7, 1337, 2026, 99, 1, 12345, 88, 1618, 314159}.

## A.4 LLM Provider 4-Audit Parsing Summary (Provider Compatibility Matrix)

TABLE A.4 presents the LLM-provider adapter parsing audit, a 20-provider × 8-column compatibility matrix that is expanded from the 4-row conference-paper version to the full 20-row version in the arXiv Appendix D (pages 18–19). The sample rows in this thesis appendix are the four primary providers used throughout the evaluation: Ollama local laptop, OpenRouter qwen2.5-family, OpenAI GPT-4-family, and Anthropic Claude 3-family. The eight audit columns verify progressively stricter structural properties of the provider's `/chat/completions` JSON response parser in Noesis's `InferencePort` adapter layer. Columns 1–4 are the four-audit core set (hence "4-audit parsing summary"): col (1) JSON parse pass — does the raw HTTP response body parse as valid JSON on the first attempt? col (2) Structured output schema compliance — when the adapter requests a `response_format={"type": "json_schema", "schema": ...}` object, does the returned text conform to the schema (Pydantic v2 validate_json succeeds)? col (3) Seeded reproducibility — does passing `seed=42` twice on identical prompt produce byte-exact identical `choices[0].message.content` strings? (This is a per-provider property, not a Noesis one; some providers do not honour seed parameters.) col (4) Usage token count agreement — does the provider's reported `usage.prompt_tokens + usage.completion_tokens` match the adapter's internal tiktoken/qwen-tokenizer count to within ±0.5%? Columns 5–8 are extended audit flags: col (5) Tool-call JSON array parse — are function-call responses parsed into an array of `ToolCall` Pydantic objects without the common "text field containing JSON array" anti-pattern? col (6) Stop-sequence honouring — does the provider stop generating immediately on the configured `<|end_of_solution|>` stop token? col (7) Temperature 0.0 near-determinism — are two runs with temp=0.0 ≥ 99% Jaccard-identical at token level? col (8) CORS + localhost compatible — can the adapter talk to the provider directly from a browser-based frontend (Next.js dashboard Capability Inspector tab) without a proxy, for providers that offer a localhost endpoint?

The key result in TABLE A.4 is that Ollama local laptop passes all eight audits with a perfect 8/8, confirming that the laptop-first deployment choice is not merely a budget expedient but also the most structurally compatible provider for Noesis's structured-output and tool-call requirements. The OpenRouter qwen2.5-family row passes 7/8, failing only seed reproducibility because OpenRouter routes requests across a load-balanced backend pool and seed parameters are not consistently forwarded to the backend model instance. OpenAI GPT-4-family passes 5/8, failing structured output JSON schema compliance for complex nested schemas (Pydantic models with 12+ fields such as the full `CapabilityToken` schema), temperature 0.0 near-determinism (documented GPT-4-family non-determinism even at temp=0.0 due to speculative decoding fallback paths), and CORS localhost compatibility (OpenAI's `/v1/chat/completions` endpoint does not allow browser-origin CORS requests for security reasons). Anthropic Claude 3-family passes 4/8, failing structured output schema compliance, seed reproducibility (Claude 3 has no seed parameter in the Messages API as of July 2026), tool-call JSON array parse (Claude returns tool invocations inside a `<function_calls>` XML tag that requires a secondary XML-to-JSON parser), and CORS localhost compatibility. The full 20-provider matrix in the arXiv Appendix D includes additional rows for Azure OpenAI, Google Gemini Advanced, Groq Llama 3.x, Together.ai, Fireworks.ai, DeepSeek API, Mistral API, Perplexity API, Replicate, Hugging Face TGI local, vLLM local, llama.cpp CLI direct, and three India-local providers (Sarvam AI OpenHathi, Reliance JioAI GenAI, Tata Neu NLP); the only additional provider with a perfect 8/8 score is llama.cpp CLI direct (which is the underlying inference engine for Ollama anyway), confirming that local-first inference is strongly preferred for Noesis's 4-audit requirements.
